### 回滚此提交 Revert

### 重置 reset

一般不用，如果需要回退，请直接使用revert。
reset和revert的 区别：
假设历史为：A — B — C (HEAD)
git reset --hard B
结果：A — B (HEAD)，C 被删除。
git revert C
结果：A — B — C — D (HEAD)，其中 D 是“撤销 C”的提交。

案例演示：如下图，目前历史有4个版本，现在直接将版本重置到【提交2】，那么【提交2】之前的提交会被直接删除，然后工作区保留最新的文件状态。

#### reset 的三种模式

1、mixed（默认，一般直接选这个就好了） 和 soft 
1）. git reset --soft 提交2 效果：
- HEAD 回到提交2
- 提交3的所有更改仍然在暂存区（就像你刚 git add 过一样）
- 后续操作：直接 git commit 就能生成一个和提交3内容完全相同的新提交（只是 commit hash 不同）
2）. git reset --mixed 提交2  效果：
- HEAD 回到提交2
- 提交3的更改从暂存区移除，变成工作区的“未暂存修改”
- 后续操作：需要重新 git add 选择要提交的文件，才能再次提交

2、hard：会彻底直接丢去之前的所有更改，一般不用。

### reset 和 revert

对于已经推送到远程仓库的提交，如果需要撤回的话，请使用revert；而对于还没有推送到远程仓库的提交，想撤回，可以使用reset，在本地调整之后再次提交，可以使得提交历史更加干净。

【案例1】：本地dev环境，线上master环境，正常的流程是在dev开发，然后没问题之后合并到master，然后在推送到线上服务器，现在正式环境master需要紧急回退到上一个版本，标准操作流程：
1. 本地切换到master分支，拉取最新状态（确保同步）。
2. 查看历史提交，确认选择需要回退到版本，执行revert进行回退。
3. 回退之后再次推送到远程master。
4. 之后在dev修复，修复完成之再次直接合并到master即可。

【案例2】只要还没有推送到远程仓库，只是在自己本地进行了提交，那么想撤回，重新提交，修改提交信息什么的，都可以直接使用reset。
- 漏改文件或者写错了提交信息
- 本地做了很多实验室的修改，想彻底放弃，回到之前好的状态

## 合并

- 每次 commit 会保存一个完整项目快照（不是差异！）。
- 分支（如 main、feature）本质上只是一个指向某个 commit 的指针。
- 当你切换分支，Git 只是把工作区文件换成该 commit 对应的快照。

所以，“合并”本质上是如何把两个不同快照的历史连接起来。


### merge
【场景】main 分支出 feature，各自有新提交，main分支在B的基础上新增了E提交，而feature在分支B的基础上新增C和D的提交。

![[Pasted image 20260518223508.png]]
现在你想把 feature 的成果整合回 main。
方法：切换到main分支，选择feature分支merger到main分支上。
```bash
git checkout main 
git merge feature
```

![[Pasted image 20260518224721.png]]

合并提交 M 包含：
- 父提交有两个：E（来自 main）和 D（来自 feature）
- 内容 = E 和 D 的最新状态的融合
- 如果 E 和 D 修改了同一文件的同一区域 → 冲突，需手动解决

✅ 优点
保留完整历史：清晰看到 feature 是何时、从哪里分出又合入的。
安全：不修改任何已有提交（commit hash 不变），适合公共分支。
❌ 缺点
历史呈“分叉状”，如果频繁小功能合并，图会很乱。


### rebase

同样是把 feature 整合进 main，但希望历史是线性的，仿佛你是在 main 最新状态之后才开发的。

操作：切换到feature分支，选择main分支进行变基。
```bash
git checkout feature 
git rebase main
```

Git 会：
- 找到 feature 和 main 的共同祖先（这里是 B）
- 把 feature 上自 B 之后的所有提交（C, D）临时保存为补丁
- 将 feature 分支指针移到 main 最新提交（E）上
- 逐个重新应用这些补丁（相当于重新执行 C 和 D 的修改）

![[Pasted image 20260518225112.png]]

这个时候main分支上的变动已经完全同步到feature分支了，然后再切换到main分支，将feature分支merger到main分支。
![[Pasted image 20260518230241.png]]

✅ 优点
历史线性、整洁，易于阅读和 git bisect 排查问题。
避免不必要的“合并提交”。
⚠️ 缺点
重写了提交历史（旧 C, D 被废弃，新 C', D' 诞生）
如果 C/D 已被推送到远程或被他人使用 → 协作灾难！



![[Pasted image 20260518225620.png]]

![[Pasted image 20260518225638.png]]

### merger和rebase选择

✅ 用 merge 当：
- 比如把dev分支合并到master分支，且这个dev分支已经推送到了远程仓库
- 希望保留完整的集成历史（谁在什么时候合了什么）
✅ 用 rebase 当：
- 在本地开发一个新的私有分支，还没有推送到远程，想整理提交然后merge到dev分支上
- 希望 PR 的历史是干净的线性提交
