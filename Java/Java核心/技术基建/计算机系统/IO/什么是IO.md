
# **1️⃣ 什么是 IO？（一句话但要真正懂）**


**IO = CPU 与「外部世界」交换数据**

  

外部世界包括：

- 磁盘（文件 IO）
    
- 网络（Socket IO）
    
- 键盘 / 鼠标
    
- 显示器
    
👉 **关键点**：

CPU **自己不会**去磁盘、不会去网卡

**必须通过操作系统 + 硬件控制器**

---

## **2️⃣ IO 为什么“慢”**

  

CPU 速度（纳秒级） vs IO 设备（微秒 / 毫秒）

|**设备**|**延迟量级**|
|---|---|
|CPU cache|ns|
|内存|~100ns|
|SSD|~100µs|
|网络|ms|

👉 所以：

  

> **IO = 等**

---

## **3️⃣ 最原始的问题出现了**

  

> CPU 在等 IO 的时候怎么办？

  

这就引出了 **IO 模型**

---

# **二、IO 模型 =「等的方式」**

  

IO 模型本质只有一句话：

  

> **当数据还没准备好时，线程怎么办？**

---

# **三、从最蠢的方式开始（Blocking IO）**

  

## **1️⃣ 阻塞 IO（Blocking IO）**

  

### **行为**

```
read(fd)
 ├─ 没数据
 │   └─ 线程阻塞（睡死）
 └─ 有数据
     └─ 拷贝到用户态，返回
```

### **特点**

- 一个线程 = 一个连接
    
- 等数据时线程啥也干不了
    

  

### **结果**

```
10 万连接
= 10 万线程
= ❌ 直接爆炸
```

💥 **不是 CPU 不够，而是线程调度 + 内存栈 + 上下文切换**

---

## **2️⃣ 为什么“早期服务器”撑不住？**

- Linux 线程栈默认 8MB
    
- 10 万线程 ≈ 800GB 内存（还没算别的）
    

---

# **四、第一轮进化：Non-blocking IO**

  

## **1️⃣ 非阻塞 IO 干了什么？**

```
read(fd)
 ├─ 没数据 → 立刻返回 EAGAIN
 └─ 有数据 → 返回数据
```

### **问题来了**

```
while (true) {
    if (read(fd) == EAGAIN) {
        // 继续问
    }
}
```

👉 **CPU 空转（忙等）**

---

## **2️⃣ 结论**

- 不阻塞线程 ✅
    
- 但浪费 CPU ❌
    

---

# **五、真正的分水岭：IO 多路复用**

  

> **一个线程，管理 N 个连接**

---

## **1️⃣ IO 多路复用在干什么？**

  

一句话：

  

> **“哪些 fd 有数据了？告诉我。”**

---

## **2️⃣ select / poll（早期）**

```
select(fds)
 ├─ 内核遍历所有 fd
 ├─ 找到有数据的
 └─ 返回
```

### **问题**

- 每次 O(n) 扫描
    
- fd 数量有限制（select）
    

---

## **3️⃣ epoll（Linux 的核武器）**

  

### **epoll 的核心变化**

|**旧**|**新**|
|---|---|
|应用反复问|内核主动通知|
|全量扫描|就绪链表|
|O(n)|接近 O(1)|

### **epoll 模型**

```
epoll_wait()
 ├─ 没事件 → 线程睡眠
 └─ 有事件 → 返回就绪 fd 列表
```

👉 **线程只在“有事”时醒来**

---

# **六、到这里，我们已经解决了什么？**

|**问题**|**是否解决**|
|---|---|
|阻塞线程|✅|
|忙等|✅|
|线程爆炸|✅|

**一个线程可以管理几万连接**

---

# **七、但这还不够：数据拷贝问题**

  

IO 还有两个阶段：

1. 数据从 **设备 → 内核缓冲区**
    
2. 数据从 **内核 → 用户态**
    

---

## **1️⃣ 同步 IO（前面讲的）**

```
epoll_wait()
read()
```

read 还是要 **自己拷贝**

---

## **2️⃣ 异步 IO（AIO）**

```
aio_read(fd, callback)
```

- 提交 IO 请求
    
- 内核完成后回调
    

  

### **Linux 的现实**

- 文件 IO 才真正异步
    
- 网络 IO 本质还是 epoll + 非阻塞
    

  

👉 所以 **“高并发服务器 ≠ 真 AIO”**

---

# **八、现在终于能回答核心问题了**

  

## **❓为什么一个程序能处理几十万连接？**

  

我们从 0 推到这里，答案已经非常清晰：

---

## **1️⃣ 连接 ≠ 线程**

  

❌ 旧世界：

```
1 连接 = 1 线程
```

✅ 新世界：

```
N 连接 = 1~少量线程
```

---

## **2️⃣ 连接本质是什么？**

```
连接 = 一个 socket fd
```

fd 只是一个 **整数**

---

## **3️⃣ epoll 让 fd 成本极低**

- fd 挂在内核红黑树
    
- 就绪事件进入链表
    
- 应用只处理“活跃连接”
    

---

## **4️⃣ 真正的限制是什么？**

|**限制**|**说明**|
|---|---|
|内存|socket buffer|
|带宽|网卡|
|业务逻辑|CPU|

**不是连接数本身**

---

# **九、各类编程语言是怎么“用上”这套能力的？**

---

## **Java**

  

### **1️⃣ Java NIO**

- Selector = epoll 封装
    
- Channel = fd 抽象
    

  

### **2️⃣ Netty**

- Reactor 模型
    
- EventLoop = epoll_wait + 回调
    
- 极少线程处理大量连接
    

  

👉 **Java 可以 10w+ 连接**

---

## **JavaScript（Node.js）**

  

### **特点**

- 单线程
    
- libuv
    
- epoll + 事件循环
    

```
while (true) {
  poll events
  execute callbacks
}
```

👉 **“单线程 ≠ 只能一个连接”**

---

## **Go**

  

### **表面**

```
go handleConn(conn)
```

### **实际**

- goroutine ≠ OS 线程
    
- runtime 内部 epoll
    
- M:N 调度
    

  

👉 goroutine 阻塞 ≠ 线程阻塞

---

## **Python**

- 原生：慢（GIL）
    
- asyncio / uvloop：epoll
    
- 框架：aiohttp / fastapi
    

---

## **C / C++**

- 直接 epoll
    
- nginx / redis / memcached
    

---

# **十、一句“本质总结”（非常重要）**

  

> **高并发的本质不是“跑得快”，而是“不傻等”**

---

## **再压缩成一句终极结论：**

  

> **操作系统提供了“一个线程监听海量 IO 事件”的能力，**

> **编程语言和框架只是把它包装成了你能用的形式。**
