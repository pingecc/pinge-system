<div class="highlight-block highlight-tip">磁盘</div>

物理上的**磁盘本身也是一大片的连续字节，会被切成很多固定大小的“块”（block），比如4kb，然后操作系统层面的文件呢，它是以块为基本单位组成的，也即一个文件 = 由多个“块”组成**，而这些块在物理磁盘上可能是连续的，也可能不是连续的。
比如假设一个磁盘：
```Bash
[块1][块2][块3][块4][块5][块6][块7][块8]
```

然后有2个文件：
- 文件A：块1 + 块5
- 文件B：块2 + 块3 + 块7

那操作系统怎么知道一个文件的内容对应分散在磁盘上的哪些块呢？**通过一个索引/目录文件，这个索引文件记录了对应文件占据磁盘上的哪些块**。拿ext4类型文件系统来说，假设要访问/home/user.txt：
- 从磁盘固定入口位置读取目录文件
- 找到根目录 / 的inode，查目录内容 home → inode 50
- 然后查 inode50 找到 home 目录的数据块
- 继续查 user.txt → inode 100
- 查 inode100 blocks = [1, 5, 20]
- 最后读取 磁盘块1、5、20

每个 文件都有一个 inode，inode = 文件的元数据，包含
```Bash
文件大小
权限
时间
数据块位置（最重要）
```
而目录的本质就是  文件名 → inode编号 的映射
```Bash
目录：
  user.txt → inode 100
  order.txt → inode 200
```

# 序列化与反序列化

将内存中复杂的结构对象写入文件，然后读取文件时可以还原成内存中的结构对象。常见解决方案：
根据场景不同，实现方式也有差异：

- **编程语言原生机制**：如Java的`Serializable`、Python的`pickle`。优点是使用方便，能自动处理复杂的循环引用；缺点是数据体积大、跨语言兼容性差，且有安全风险。
    
- **标准数据格式**：如JSON、XML、YAML。它们是纯文本且可读，本质是将逻辑结构转化为嵌套的键值对，通过**结构嵌套**来表达关系，天然规避了指针问题。
    
- **高效二进制协议**：如Protocol Buffers、Thrift、Avro。它们采用**ID与类型分离**的设计，预先定义ID对应的字段类型，数据体积小、解析极快，非常适合高性能场景。
    
- **数据库引擎**：数据库的**缓冲池**和**页**机制是更底层的实现。它将内存结构（B+树节点）直接映射到磁盘页上，通过**偏移量**而非内存地址来维持逻辑关系，读取时通过内存映射文件（mmap）或手动加载来还原。


通过以上案例可以看出，将内存逻辑结构写入文件并还原的关键在于：

1. **定义清晰的协议**（用什么格式、如何标记类型、如何处理变长字段）。
    
2. **将指针/引用转换为可持久化的标识**（如 ID、路径等）。
    
3. **反序列化时采用两阶段过程**：先创建对象池，再修复引用关系。
    

无论是使用 JSON 这样的文本格式，还是手动构建二进制协议，核心思想都是**数据编解码 + 引用解析**。




## 磁盘IO

在一台计算机当中，关于数据的存取，CPU本身 并不参与“数据搬运”，只是“发指令 + 控制”，**数据都是直接通过IO总线/DMA，在磁盘和内存之间传递**。当需要计算时，才内存 → CPU缓存 → CPU
1. 从磁盘上读取数据：磁盘——>内存
```Bash
1️⃣ CPU 发起系统调用（read）
2️⃣ 操作系统告诉磁盘控制器：“把这块数据读出来”
3️⃣ 磁盘控制器通过 DMA：
    👉 直接把数据写入内存（Buffer）
4️⃣ CPU 收到中断通知：“数据读好了”
5️⃣ CPU 才开始使用这块数据（加载到寄存器/缓存）
```

2. 数据写入磁盘：内存——>磁盘
```Bash
1️⃣ CPU 修改内存中的数据
2️⃣ 发起写请求（write）
3️⃣ 操作系统通知磁盘控制器
4️⃣ DMA 把数据：
    👉 从内存写入磁盘
5️⃣ 写完成（可能有缓存/延迟）
```

2、操作系统发起IO从磁盘上的读取数据时，不是按“字节读”，而是按“块（Page）为基本单位读”，

当向数据库发起一次查询时，MySQL 会优先在内存（Buffer Pool）中查找对应的数据页，如果命中则直接返回；如果未命中，则通过 IO 从磁盘读取对应的数据页（通常是16KB）到内存，再进行查询。由于磁盘 IO 的成本远高于内存访问（通常差几个数量级），因此数据库性能的瓶颈主要在于磁盘 IO。SQL 执行的快慢，本质取决于执行过程中访问的数据页数量以及访问方式（顺序 IO / 随机 IO）。因此数据库优化的核心目标是：

> 👉 **减少访问的数据页数量 + 尽量将随机 IO 转为顺序 IO**
