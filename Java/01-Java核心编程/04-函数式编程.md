Java“支持函数式风格”：函数式接口+Lambda语法支持。

# 函数接口发展历程
### 类
Java 的世界观：一切行为必须挂在“类”上，在 Java 的设计哲学里：代码不能裸奔，行为必须属于某个对象。


最朴素的例子：

```Java
class Adder {
    int add(int a, int b) {
        return a + b;
    }
}
```

你想“做一件事”，必须：
1. 定义一个类
2. new 一个对象
3. 调一个方法

问题出现了：如果我只想“传一段行为”呢？

比如：排序。

```
Collections.sort(list, ???);
```

这里 ??? 是什么？

- 不是数据
- 是**规则 / 行为**
👉 Java 早期唯一能传的“行为载体”只有：**对象**

早期的解决方案：接口 + 实现类（重量级）

  1️⃣ 用接口抽象“行为”

```Java
interface Comparator<T> {
    int compare(T o1, T o2);
}
```
2️⃣ 实现它

```Java
class UserComparator implements Comparator<User> {
    @Override
    public int compare(User a, User b) {
        return a.getAge() - b.getAge();
    }
}
```

3️⃣ 使用

```
Collections.sort(users, new UserComparator());
```

**问题来了：**
- 这个类只用一次
- 文件一堆
- 行为和使用地点分离
👉 **类变成了“行为的包装壳”**

### 匿名内部类

只想临时实现一个接口或者抽象类（比如 Runnable、Comparator），又不想专门写一个完整类，就可以用匿名内部类。

```Java
// 返回对应实现类的实例对象
new 父类构造器() 或 new 接口() { 
	// 重写方法 
}
```

例如：

```Java
Collections.sort(users, new Comparator<User>() {
    @Override
    public int compare(User a, User b) {
        return a.getAge() - b.getAge();
    }
});
```



匿名内部类：

- ✅ 解决了“类太多”的问题
- ❌ 没解决“冗长”
- ❌ 没解决“行为不是一等公民”
### 函数式接口 与 Lambda语法

>在Java正是因为同时有了函数式接口和Lambda语法，可以直接通过lambda语法：`(参数列表) -> { 函数体 }`去描述一段行为/规则，把它当作值进行传递，而对应的函数式接口为编译器提供了类型推断。

函数式接口：只有一个抽象方法的接口。 （default 方法不算）
  >在实际开发中，如果确定定义只有一个抽象方法的接口时，建议加上`@FunctionalInterface` 注解，给编译器用的，作用是：限制接口只能有一个抽象方法;为类型推断提供前提，lambda语法。


**在Java中，函数式接口和Lambda语法是相互依赖的**，如果只有函数式接口，没有Lambda语法，那么这个所谓的函数式接口和一个只有一个抽象方法的普通接口没啥区别，实用价值几乎为0，例如下面代码，和以前的匿名内部类的写法没啥区别。
```Java
list.stream()
    .filter(new Predicate<Integer>() {
        @Override
        public boolean test(Integer x) {
            return x > 10;
        }
    })
    .map(new Function<Integer, Integer>() {
        @Override
        public Integer apply(Integer x) {
            return x * 2;
        }
    });
```

而如果只有所谓的Lambda语法，没有函数式接口，在Java中也无法成立，假设 Java 直接学 JS / Python：
```Java
(x, y) -> x + y
```
由于Java是强类型的，这就导致这个 Lambda 是什么类型？方法参数和返回值的类型分别又是什么？这个函数能赋值给谁？
而有了函数式接口：
> **只要一个接口只有一个抽象方法，它就可以代表一个函数类型**

```Java
@FunctionalInterface
interface Function<T, R> {
    R apply(T t);
}
```

**接口类型 = 函数签名的“类型载体”**
```Java
Function<Integer, Integer> f = x -> x * 2;
```
等价于：
```Java
Function<Integer, Integer> f = new Function<>() {
    @Override
    public Integer apply(Integer x) {
        return x * 2;
    }
};
```


现在，我们把匿名内部类再看一眼：

```Java 
new Comparator<User>() {
    @Override
    public int compare(User a, User b) {
        return a.getAge() - b.getAge();
    }
}
```


1️⃣ Java 编译器根据接口类型：`Comparator<User>`，就可以完全推断出，
- 方法名固定：compare
- 返回值类型确定

只剩下：参数 + 逻辑
 Lambda 就是“只写剩下的部分”

```Java
(user1, user2) -> user1.getAge() - user2.getAge()
```

用上去：

```Java
Collections.sort(users,
    (a, b) -> a.getAge() - b.getAge()
);
```

当然这只是语法糖，Lambda 在 JVM 层面并不是函数，它最终仍然会被转成， 一个实现了函数式接口的对象，只是：
- 编译器帮你生成
- 写法极度精简

  

> **Java 的 Lambda = 行为的“延迟对象化”**

  

- 写的时候像函数
    
- 用的时候是对象
    
- JVM 仍然是面向对象的

这就是为什么：

- Java 叫“支持函数式风格”
    
- 而不是“函数式语言”
    

## 四个核心函数式接口

1. `Function<T, R>` 类比成 `y=f(x)`函数，给定一个输入参数x，就可以得到一个输出值y。
2. `Predicate<T>` ，给定输入参数x，返回值固定boolean类型。
3. `Consumer<T>`，给定参数x，无返回值。消费者模型。
4. `Supplier<R>`，无输入参数x，返回一个值。生产者模型。

先理解为什么Java只设计了这四个函数式接口：

是因为从“数据流动”的角度看，所有计算行为都可以被归约为：**有没有输入？有没有输出？**
而这 4 个接口 正好覆盖了所有“最小完备”的函数形态。



一、别从 API 看，从“计算模型”看

一个计算，本质上干了什么？

```
拿到数据 → 处理 → 可能产生结果 / 副作用
```

于是自然出现两个维度：

|**维度**|**可能值**|
|---|---|
|是否有输入|有 / 无|
|是否有输出|有 / 无|

---
这两个维度一组合，把组合列出来 👇

|**输入**|**输出**|**对应接口**|**含义**|
|---|---|---|---|
|有|有|**Function<T, R>**|转换|
|有|无|**Consumer**|消费 / 副作用|
|无|有|**Supplier**|生产|
|有|boolean|**Predicate**|判断|

你会注意到一个“特殊点”：

👉 Predicate 本质上是 Function<T, Boolean>

但 Java **把它单独拎出来了**。

### Function —转换者

```
T -> R
```

这是最纯粹的函数意义：

- 输入一个值
- 输出一个值
- 不关心副作用
Stream 里：
- map
- flatMap
### Predicate —判断者

```
T -> boolean
```

它的地位之所以特殊，是因为：

- 判断在计算中极其常见
- boolean 有强语义
- Stream 里 filter 完全围绕它设计

如果只用 Function<T, Boolean>：
- 语义弱
- 可读性差
- API 不友好

👉 所以 Predicate 是**语义型拆分**


###  Consumer ——消费者
只干事，不给结果

```
T -> void
```

它表达的是：
- 日志
- 输出
- 修改外部状态
- IO
Stream 里：
- forEach
👉 **这是 Java 承认“副作用不可避免”的地方**


###  Supplier —生产者

```
() -> T
```

它看起来最不起眼，但非常关键：
- 延迟计算
- 懒加载
- 工厂
- 随机数、时间

  

Stream / Optional / 并发里大量使用。



### Runnable / Callable 是历史遗留

如果函数式接口和Lambda语法在一开始就推出，那么其实没有必要单独设计`Runable` 和 `Callable` 接口

```
Runnable: () -> void
Callable: () -> T
```

- Runnable ≈ Consumer
- Callable ≈ Supplier
    
但为了兼容，只能保留。
