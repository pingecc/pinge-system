 现代主流的JVM（如HotSpot/OpenJDK、Oracle JDK）在主流操作系统（Windows、Linux、macOS）上，都采用 **“1:1”的线程模型**，也叫**内核线程模型**。

- **一个Java线程** 直接对应 **一个操作系统内核线程（OS Thread）**。
# 进程和线程

进程：操作系统把一个程序，也即磁盘上的符合某种格式的文件加载至内存，然后需要有**一个结构对象来表示这个程序**，比如分配了多少内存，打开了多少文件等等，这样的结构对象操作系统就把它叫做进程。

线程：在内核层面，其实不区分进程和线程，都是同一个结构对象，task_struct，在早期，一个进程就是一个执行单元，只是后来进行了扩展，一个进程可以有多个执行单元，这些执行单元共享一个资源，然后有有自己独立的栈，然后就取了一个名字叫线程，如果没有多线程的话，其实一个进程就是一个线程，一个执行单元。>多个 task **共享同一个 mm_struct(地址空间) **

```Bash
        [ mm_struct A ]
         /     |     \
   task1   task2   task3
   (线程)  (线程)  (线程)

👉 这三个 task → 被称为“一个进程”
```
> ✔ **进程 = 资源容器**
> ✔ **线程 = 执行单元**


多线程：在同一个进程资源里创建多个线程（task）
- 提高CPU的利用率，因为在一个task的执行过程中并不是无时无刻都是占用CPU的，对于一些网络IO或者磁盘IO等需要等待的等操作，CPU可以去执行其它线程。
- 资源消耗问题：线程的创建和切换是消耗资源的
- 安全问题：多线程并发访问同一个资源可能会带来数据不一致问题。


## Thread类

创建线程的方式就一种，就是new 一个Thread对象，然后给它传一个函数用来执行具体的逻辑，在Java中这个函数通过Runnable接口或者Callable接口进行包装，一个是没有返回值，一个是有返回值。

1. 获取当前线程

`Thread main = Thread.currentThread();`


2. 线程的名字

可以在创建线程或者创建线程之后给线程设置名字，方便后期排查错误。

3. 线程的优先级

可以设置，但是基本不用，因为最终线程的调度还是由底层操作系统和JVM实现决定，即使设置了优先级，也无法保证高优先级一定优于低优先级的线程执行，无法预测，一般是通过设置不同的线程池进行资源的隔离来控制优先级。

4. 线程的让步 yield

同样不可靠，不可预测，程序中也不应该依赖它来控制程序的正确性，属于早期 JDK 为了“手动控制线程”而留下的残留方法，实际作用微乎其微且不可移植。


5. 线程的休眠  sleep

**对让出 CPU 非常有用，比 `yield()` 可靠得多，**
`static native void sleep(long millis)`，底层调用操作系统的原生睡眠函数，操作系统会将当前线程**从运行队列移出，放入定时器等待队列**，此时该线程不会占用CPU，调度器会立即切换其它可运行线程，当定时器到期或线程被中断（如 `interrupt()` 调用），操作系统会重新将线程放入运行队列。

6. 线程的结束
- 让线程的run方法结束，无论是return结束，还是抛出异常结束，都可以
- stop() ，强制让线程结束，不推荐
- 通过判断Thread类的`isInterrupted()`标记位，主动退出。
## 等待与唤醒

> **线程的等待/唤醒，本质就是：从 CPU 运行队列移除 → 条件满足后再放回运行队列**，底层依赖操作系统提供的阻塞与唤醒机制（如 futex）

```bash
Java → JVM → park()
       ↓
   futex_wait
       ↓
线程进入内核阻塞队列
       ↓
从 runqueue 移除
```

- 阻塞：Java代码主动调用 `LockSupport.park()` 或  `obj.wait()`  ➡️   JVM底层调用操作系统提供的阻塞机制，将该线程从运行队列中移除进入阻塞队列
- 唤醒：Java代码主动调用 `LockSupport.unpark(thread)` 或 `notify()` ➡️ JVM底层调用操作系统的唤醒机制，将线程从阻塞队列移入可运行队列，等待重新调度

<div class="highlight-block highlight-tip"> wait与notify机制</div>
1. 等待
```java
synchronized (obj) {
    obj.wait();
}
```

JVM 背后做的工作：  `ObjectMonitor::wait()`
- 当前线程释放锁 → 不再持有 monitor
- 加入等待队列（WaitSet）obj.monitor.waitSet.add(thread)
- 挂起线程，JVM 会调用操作系统：Linux：futex 或者 park()，从运行队列移除

2. 唤醒

```java
obj.notify();
```
JVM 从从 waitSet 取一个线程：
- 调用操作系统的unpark / futex_wake，移入运行队列

3. 为什么 **wait 必须在 synchronized 里？**

因为 wait操作依赖对象的 monitor(监视器；每个对象都有一个内置的监视器)，它**只有获取到了这个监视器，也即获取到了锁，才能调用 wait()/notify()**，而只有当线程进入到 `synchronized` 代码块或方法时，它会尝试获取该对象对应的 monitor 锁

```java

    owner
    entryList（竞争锁的线程）
    waitSet（等待条件的线程）
}
```


4. LockSupport
```java
LockSupport.park()
LockSupport.unpark(thread)
```

- 不依赖锁
- 底层直接用 futex
- 更灵活（AQS 用它）



# 并发三大问题
理解并发面临的三大问题以及CPU层面提供了哪些机制来解决，然后Java层面又是如何解决的。

|**问题**|**本质**|
|---|---|
|原子性|操作不能被打断|
|可见性|一个线程修改，其他线程能看到|
|有序性|指令执行顺序符合预期|
1、 原子性
-  CPU提供CAS、lock等指令，
- Java层面对应 `AtomicInteger.incrementAndGet()`，底层可能是CAS或者lock指令

2、可见性
- CPU层面它有缓存一致性协议（ MESI），用来保证数据被修改后最终可见性。背景：因为CPU里有寄存器、缓存，当数据被修改后， CPU会发消息告知，标记缓存、寄存器里的数据已经失效，等下次读取时会再次重新从内存里读取即可。但是它这个是最终可见性，可能其它CPU还是会从寄存器里读取，所以CPU层面提供了内存屏障机制，它也是CPU指令，可以实现：禁止指令重排序、机制缓存/寄存器优化，强制某些操作对其它线程可见。
- Java层面利用了CPU的这个缓存一致性协议，通过插入内存屏障指令保证可见性和有序性，对应的机制就是volatile关键字，

3、有序性
- CPU层面为了提高指令执行效率，可能并不会按照指令的顺序来执行，在高并发场景下可能会出现问题；然后CPU层面提供了内存屏障相关的指令（fence）可以禁止指令乱序



# 锁

线程的**阻塞与唤醒依赖**的是操作系统提供的阻塞与唤醒机制，而锁依赖的是**CPU提供的原子指令：CAS，lock**，而Java 锁**优先在用户态（CAS + 自旋）解决问题**，避免线程阻塞，只有竞争激烈时才依赖操作系统的阻塞/唤醒机制（futex）进行线程的挂起与唤醒


```bash

---简单获取锁，竞争不激烈时
线程A
  ↓
CAS 成功
  ↓
直接执行


----竞争激烈时，
线程B 自旋失败
  ↓
进入 AQS 队列
  ↓
LockSupport.park()
  ↓
futex_wait（进入内核）
  ↓
线程阻塞
```

关于锁的分类很多种，但是没有必要关注，都是应用层面概念性的东西：可重入锁、不克重入锁、乐观锁、悲观锁、公平锁、非公平锁、互斥锁、共享锁。
Java中常用的锁工具：synchronized、ReentrantLock

## synchronized

基于对象的Monitor（监视器）实现，自动在方法退出或异常时释放锁。

```Java
// 同步方法（实例方法）
public synchronized void method() {
    // 临界区
}

// 同步静态方法（类锁）
public static synchronized void staticMethod() {
    // 临界区
}

// 同步代码块
public void method() {
    synchronized (this) { // 或任意对象作为锁
        // 临界区
    }
}
```

##  ReentrantLock

手动加锁和解锁，更加灵活

```Java
private final ReentrantLock lock = new ReentrantLock();

public void method() {
    lock.lock(); // 获取锁
    try {
        // 临界区
    } finally {
        lock.unlock(); // 必须在 finally 中释放！
    }
}
```


# 线程池

和数据库连接池的相似，使用一个集合来存储大量线程对象：
- 复用线程对象，避免线程频繁的创建和销毁，提供系统性能
- 作为一种**资源的隔离**，对不同业务的资源使用进行限制和隔离，互不影响，通过控制线程数量、队列容量和拒绝策略，实现业务优先级的间接控制，从而避免非核心任务抢占核心业务资源。




## Executors
JDK中基于Executors提供了很多种线程池，了解下，实际用的少。

- newFixedThreadPool
- newSingleThreadExecutor
- newCachedThreadPool
- newScheduleThreadPool
- newWorkStealingPool

## ThreadPoolExecutor

通过ThreadPoolExecutor来自定义创建一个线程池，用的多

ThreadPoolExecutor提供的七个核心参数

```java
public ThreadPoolExecutor(
    int corePoolSize,           
    int maximumPoolSize,       
    long keepAliveTime,         
    TimeUnit unit,              
    BlockingQueue<Runnable> workQueue,  
    ThreadFactory threadFactory,         
    RejectedExecutionHandler handler) {  
}
```

- **corePoolSize（核心线程数）**，线程池长期维持的最小线程数量。即使空闲，也不会被回收（除非设置 allowCoreThreadTimeOut(true)）
- **maximumPoolSize（最大线程数）**：线程池允许创建的最大线程数量。当任务队列满时，会创建临时线程（超过 corePoolSize 的部分）来处理任务。
-  **`workQueue`（任务队列）**：- 用于缓存等待执行的任务，常见类型：
    - `ArrayBlockingQueue`：有界队列（推荐！防内存溢出）
    - `LinkedBlockingQueue`：无界队列（默认，但可能 OOM）
    - `SynchronousQueue`：不存储任务，直接交给线程（如 `newCachedThreadPool`）
- **handler（拒绝策略）**：当线程数达上限 + 队列满时，新任务如何处理？
	- AbortPolicy（默认）：抛出 RejectedExecutionException
	- CallerRunsPolicy：由提交任务的线程自己执行（降低提交速度）
	- DiscardPolicy：静默丢弃任务
	- DiscardOldestPolicy：丢弃队列中最老的任务，重试提交
- keepAliveTime + unit：非核心线程在空闲时的最大存活时间。超时后自动销毁，释放资源。
- threadFactory：自定义线程创建逻辑（如命名、优先级、异常处理）。

线程池的使用难度不大，难度在于线程池的参数并不好配置，可以使用hippo4j等工具对对线程池进行监控，动态的调整线程池相关参数（因为线程池提供了动态修改核心属性的方法）
# 并发工具类

`java.util.concurrent`（简称 JUC）是 Java 为高并发、多线程编程提供的**工具包**，从 JDK 5 开始引入。它封装了线程安全的数据结构、高效的同步机制、灵活的线程池以及异步编程模型，极大简化了并发程序的开发，避免直接使用底层的 `synchronized`、`wait/notify` 和 `Thread` 原生方法

## 原子类

提供了原子性的操作，可以在多线程环境下安全地进行更新操作，底层利用 CAS（Compare And Swap）机制来保证操作的原子性，避免了传统锁机制的开销。

```java
private static final AtomicBoolean running = new AtomicBoolean(false);  
public static void main(String[] args) {  
    for (int i = 0; i < 10; i++) {  
        try {  
            TimeUnit.SECONDS.sleep(1);  
        } catch (InterruptedException e) {  
            throw new RuntimeException(e);  
        }  
        if (running.compareAndSet(false, true)) {  
          new Thread(() -> {  
              System.out.println(Thread.currentThread().getName() + "- 开始执行-----");  
              try {  
                  TimeUnit.SECONDS.sleep(3);  
              } catch (Exception e) {  
                  e.printStackTrace();  
              } finally {  
                  running.set(false);  
                  System.out.println(Thread.currentThread().getName() + "- 执行结束-----");  
              }  
          }).start();  
        } else {  
            System.out.println(i + "-尝试执行失败-----");  
        }  
    }  
  
}
```

## 同步辅助器

### CountDownLatch

应用场景：主线程等待一定数量的子线程执行完之后再去处理后续逻辑。
假设现在有三个任务需要并行处理，然后需要等待这三个任务都处理完成了，主线程再继续处理后面的逻辑，创建一个CountDownLatch，设置为3，在每个子任务执行结束之后执行减1操作，然后主线程调用 await()阻塞等待计数器变为0。

```Java
import java.util.concurrent.CountDownLatch;

public class CountDownLatchExample {
    public static void main(String[] args) throws InterruptedException {
	int numberOfTasks = 3;
	CountDownLatch latch = new CountDownLatch(numberOfTasks);
	
	
	for (int i = 0; i < numberOfTasks; i++) {
		final int taskId = i;
		new Thread(() -> {
			try {
				System.out.println("任务 " + taskId + " 开始执行");
				Thread.sleep((taskId + 1) * 1000); 
				System.out.println("任务 " + taskId + " 执行完毕");
			} catch (InterruptedException e) {
				Thread.currentThread().interrupt();
			} finally {
			   // 注意要在finally中执行减1操作
				latch.countDown(); // 计数器减1
			}
		}).start();
	}
	
	System.out.println("等待所有任务完成...");
	// 主线程阻塞等待计数器变为0
	latch.await(); 
	System.out.println("所有任务已完成！");
    }
}
```

### CyclicBarrier

用于多个线程之间互相等待，当其中一个线程调用了 `barrier.await();`，就会等待剩下的线程也调用 `barrier.await();`，当最后一个线程调用 `barrier.await();`所有线程被释放继续执行，`barrier.await();` 可以多次使用。

例如：`new CyclicBarrier(3, f() )`，
- 设置相互等待的线程数量为3
- 只要其中一个线程调用了 await()，则阻塞，直到另外2个线程也调用了await()
- 当第三个线程调用了await()，所有线程释放，继续执行
- 在后续执行过程中可以再重复一轮上述等待行为。


```Java
import java.util.Random;
import java.util.concurrent.BrokenBarrierException;
import java.util.concurrent.CyclicBarrier;

public class GameSyncExample {
    public static void main(String[] args) {
        int playerCount = 5;
        Random random = new Random();
        
        CyclicBarrier barrier = new CyclicBarrier(playerCount, () -> {
            System.out.println("所有玩家已准备就绪，游戏开始！");
        });
        
        for (int i = 0; i < playerCount; i++) {
            final int playerId = i;
            new Thread(() -> {
                try {
                    System.out.println("玩家 " + playerId + " 进入房间");
                    
                    // 模拟玩家准备时间
                    Thread.sleep(random.nextInt(3000));
                    System.out.println("玩家 " + playerId + " 准备完成");
                    
                    // 等待其他玩家
                    barrier.await();
                    
                    System.out.println("玩家 " + playerId + " 开始游戏");
                    
                } catch (InterruptedException | BrokenBarrierException e) {
                    Thread.currentThread().interrupt();
                    e.printStackTrace();
                }
            }).start();
        }
    }
}
```

### Semaphore

用于控制并发访问资源的线程数量。
 例如：`Semaphore semaphore = new Semaphore(3);`设置最多只能有三个线程可以同时访问

```Java
import java.util.concurrent.Semaphore;

public class SemaphoreBasicExample {
    public static void main(String[] args) {
        // 创建一个有3个许可的信号量
        Semaphore semaphore = new Semaphore(3);
        
        // 创建10个线程模拟资源访问
        for (int i = 0; i < 10; i++) {
            final int threadId = i;
            new Thread(() -> {
                try {
                    System.out.println("线程 " + threadId + " 尝试获取许可");
                    semaphore.acquire(); // 获取许可
                    System.out.println("线程 " + threadId + " 获得许可，开始执行");
                    
                    // 模拟资源使用
                    Thread.sleep(2000);
                    System.out.println("线程 " + threadId + " 执行完成");
                    
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    e.printStackTrace();
                } finally {
                    semaphore.release(); // 释放许可
                    System.out.println("线程 " + threadId + " 释放许可");
                }
            }).start();
        }
    }
}
```
