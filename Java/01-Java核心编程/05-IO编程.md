


# 对象序列化

所谓的对象序列化其实就是把一个Java对象，也即内存中的结构数据转换成字节流，以便可以：
- 保存到文件中
- 通过网络传输
而反序列化（Deserialization）则是将字节流重新转换回对象，也即内存中的结构数据。
但是Java 原生序列化存在安全风险（反序列化漏洞）和性能问题，现在一般采用其他的数据格式，比如 JSON（Jackson/Gson）、Protobuf、Kryo 等替代方案。
- Serializable 
- transient
- ObjectOutputStream
- ObjectInputStream
<div class="highlight-block highlight-tip">下面展示下如果需要使用Java原生的方式进行序列化 </div>

1. 对象实现 `Serializable` 接口

2. 使用 `ObjectOutputStream` 类完成对象的序列化和反序列化

```Java
import java.io.*;

class Person implements Serializable {
    private static final long serialVersionUID = 1L;
    private String name;
    private int age;
    private transient String secret; // 不会被序列化

    public Person(String name, int age, String secret) {
        this.name = name;
        this.age = age;
        this.secret = secret;
    }

    @Override
    public String toString() {
        return "Person{name='" + name + "', age=" + age + ", secret='" + secret + "'}";
    }
}

public class Main {
    public static void main(String[] args) throws Exception {
        Person p = new Person("Alice", 30, "mySecret");

        // 序列化 转成字节流之后写入文件 person.er
        try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("person.ser"))) {
            oos.writeObject(p);
        }

        // 反序列化
        try (ObjectInputStream ois = new ObjectInputStream(new FileInputStream("person.ser"))) {
            Person p2 = (Person) ois.readObject();
            System.out.println(p2); // secret 字段为 null
        }
    }
}
```

说明：
1. 序列化写入文件 `person.er`，这个后缀可有可无，无所谓，只是约定俗成 `er` serialization 缩写，表示通过Java序列化的
2. `Serializable` 本身是一个标记接口，接口中没有任何方法，如果一个对象需要被序列化，则必须实现该接口，否则在使用 `ObjectOutputStream`进行序列化时则报错。下面是 `ObjectOutputStream` 的`writeObject` 方法说明。
![[Pasted image 20260119202748.png]]
3. `serialVersionUID`  在序列化时 Java 会把对象的 serialVersionUID 值写入字节流，而在反序列化时Java 会：读取字节流中的 serialVersionUID，与当前类的 serialVersionUID 比较只有两者相等，才允许反序列化；否则抛出：`java.io.InvalidClassException: local class incompatible`
	1. long 类型的静态常量，必须命名为 serialVersionUID。
	2. 建议显示声明。
		1. 如果没有声明，那么Java 在序列化时会基于当前类的结构自动生成一个
		2. 但是：只要修改了类的任何结构（比如加/删字段、改访问修饰符），自动生成的 UID 就会变！即使逻辑上“兼容”（比如只加了一个可选字段），最终反序列化也会失败！
		3. 而如果显示声明了，即使增加了字段，只要 serialVersionUID 的值没有变，和序列化文件中的一样，还是反序列化就能成功。
			1. 新增的字段会被赋予默认值
			2. 已有字段正常还原
4. 可以使用 `transient` 关键字标记不想被序列化的字段（如密码、临时缓存等）。
```java
private transient String password;
```


<div class="highlight-block highlight-warn">疑问：为什么需要有 Serializable 这个标记接口，我使用ObjectOutputStream类完成序列哈，传入了一个Java对象，直接给我序列化不就行了，为什么还要专门标记下这个对象是否可以序列化？</div>
主要涉及到安全问题，所以 Java采用：显式优于隐式（Explicit is better than implicit）的设计

 一、安全考虑（Security）

**不是所有对象都适合被序列化**。有些对象包含敏感信息（如密码、密钥）、系统资源（如文件句柄、网络连接、线程），或者其状态无法用字节流准确还原。

- 如果 Java 默认允许所有对象序列化，开发者可能**无意中把不该暴露的数据写入磁盘或网络**。
- 通过强制实现 `Serializable`，Java 要求开发者**主动确认**：“我清楚这个类可以安全地被序列化”。
- 技术限制；并非所有对象都能“有意义地”序列化，有些对象的状态依赖于当前 JVM 的运行环境比如：
	- `Thread`：线程不能跨 JVM 恢复；
	- `FileInputStream`：底层是操作系统文件描述符，无法在另一台机器上重建；
	- 匿名内部类：可能持有外部类的引用，导致意外序列化大量无关对象。
	如果 Java 自动序列化这些对象，要么失败，要么产生无意义甚至危险的结果。


想象一下：

```java
class BankAccount {
    private String accountNumber;
    private String password; // 敏感信息！
}
```

如果 Java 默认允许序列化，而你又不小心把 `BankAccount` 对象写入了日志文件或缓存，**密码就可能以明文形式泄露**（即使你用了 `transient`，但如果你忘了呢？）。

通过要求实现 `Serializable`，Java 强制你停下来思考：

> “这个类真的应该被序列化吗？哪些字段要排除？是否需要自定义 `writeObject`/`readObject`？”

---



对比其他语言的设计

- **Python 的 `pickle`**：默认大多数对象可序列化，但也因此更容易出现安全漏洞和反序列化错误。
- **Java 的设计更保守**：宁可让开发者多写一行代码（`implements Serializable`），也要避免潜在风险。

> 这体现了 Java 的设计哲学：**安全性和可控性优先于便利性**。


<div class="highlight-block highlight-warn">疑问：为什么非的要有 serialVersionUID？在反序列化时直接尽量反序列化，比如没有的字段就赋默认值不就好了，为啥需要显示的使用serialVersionUID来判断是否可以反序列化呢？</div>
**能反就反，没有的字段给默认值，多的字段忽略**”——其实在很多现代序列化框架（如 JSON、Protobuf、Kryo）中确实是这样做的。但 Java 原生序列化之所以引入 `serialVersionUID` 并采取**严格校验策略**，背后有深刻的设计考量。

Java 序列化的目标：**精确还原对象状态**

Java 原生序列化的设计初衷是：

> “在另一个 JVM 中**完全重建出一个语义等价的对象**，包括所有字段、内部状态、甚至对象图结构。”

这意味着：

- 它不是“传输数据”，而是“迁移对象”。
- 如果类结构变了，**对象的语义可能已经不同了**，盲目反序列化会导致逻辑错误。

🌰 举个危险的例子：

```java
// v1
class BankAccount implements Serializable {
    private static final long serialVersionUID = 1L;
    private double balance; // 余额
}
```

你序列化了一个 `balance = 1000.0` 的账户。

后来你重构代码：

```java
// v2（错误地重命名字段）
class BankAccount implements Serializable {
    private static final long serialVersionUID = 1L;
    private double amount; // 改名叫 amount 了！
}
```

如果没有 `serialVersionUID` 校验（或自动生成的变了），反序列化时：

- `balance` 字段不存在 → 被忽略
- `amount` 是新字段 → 默认为 0.0

结果：**用户余额从 1000 变成 0！资金丢失！**

👉 这种“静默失败”比直接报错更可怕！

所以 Java 选择：**宁可失败，也不返回一个“看起来对但实际错”的对象**。

---

**自动兼容判断太难，容易出错**

你可能会说：“那 Java 可以智能一点啊，比如只允许加字段，不允许删或改类型”。

但现实中，**“兼容性”是非常复杂的语义问题**，无法仅靠字段增减判断：

|修改类型|是否兼容？|说明|
|---|---|---|
|新增非 `transient` 字段|✅ 通常兼容|反序列化时设默认值|
|删除字段|❌ 不兼容|数据丢失|
|改变字段类型（`int` → `long`）|⚠️ 可能兼容|但 `ObjectInputStream` 不支持自动转换|
|把 `List<String>` 改成 `List<Integer>`|❌ 严重不兼容|类型擦除后运行时才发现错误|
|修改继承关系|❌ 高风险|父类字段顺序变化可能导致错位|

Java 原生序列化**没有能力安全地处理这些情况**，所以干脆交由开发者通过 `serialVersionUID` **手动控制版本边界**。

> 💡 换句话说：**“兼容性”是业务逻辑问题，不是技术问题**。只有类的作者知道哪些变更可以接受。

---

`serialVersionUID` 是开发者的“契约开关”

当你显式声明 `serialVersionUID = 1L`，你其实在告诉 JVM：

> “我确认当前类与 `serialVersionUID=1L` 的旧版本是**兼容的**，可以安全反序列化。”

如果你做了破坏性修改，你就应该：

```java
private static final long serialVersionUID = 2L; // 主动升级版本号
```

这样旧数据就无法反序列化，**强制你写迁移逻辑**（比如读旧格式、转新对象）。

这其实是一种**防御性编程**：把潜在错误暴露在开发/测试阶段，而不是上线后静默出错。
