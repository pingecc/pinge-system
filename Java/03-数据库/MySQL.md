# 数据模型与设计
### 关系模型与范式设计
数据库的目标就是用结构化的方式来描述现实世界，进行持久化。
1、在进行关系型数据库的设计时，通常基于实体关系模型（ER）来设计：实体、属性、关系。
实体与实体之间的关系：
- 一对一（1:1）：
比如 用户 —— 用户详情，如果字段不是特别多的话，一般会直接合并成一张表。
- 一对多（1:N）：用户——订单，常常会在另外一张表通过ID去关联对应的表，比如在订单表添加`user_id` 
- 多对多：(N:N)：订单——商品，会额外通过一张中间表去关联，比如存对应的订单ID和商品ID

2、关于范式与反范式设计

- 范式设计：无需刻意去记住什么第一范式、第二范式、第三范式，只需要知道范式的目标：**消除数据冗余 + 避免数据异常**，具体表现为：**把一些在多个表共有的属性尽可能的抽离出来放在单独的一个表**，这样避免在多个表中存相同的数据（冗余），也避免修改共同属性值时要修改很多行，且不能删除。
- 反范式设计：由于关联表比较消耗性能，所以为了能够查询的更快，很多时候会进行反范式设计，也即把一些经常需要查询的字段会进行冗余设计。


### MySQL设计说明

1. 命名与字符集
- 不管是数据库名、还是表名、还是字段名，**建议直接全部小写 + 下划线**（如 `order_service_db`），避免大小写敏感问题。
- 字符集选择 `utf8mb4。  （它可以表示更多的字符集，可能有人说选择 utfbmb3 在存储上更加节约空间，其实对于绝大多数字符，像中文，英文，数字这 2 者占用的字节是一样的，只是对于一些特殊字符，utf8mn4 会占用 4 字节）
- 排序集（也叫字符比较规则，指的是字符之间的大小比较，在查询时如果需要对字符列进行排序时会使用到）选择`utf8mb4_unicode_ci`

2. 主键
- MySQL InnoDB：建议用单调递增整数，避免 UUID 导致页分裂。
- **外键：通常不使用，应用层保证一致性**。其它约束也是一样，应用层来保证，语义清晰容易维护。

1. 反范式设计
- 保证一致性：
	- 相关表更新时，同时更新当前表的冗余字段
	- 接受短暂不一致：异步更新，通过消息队列或数据库 trigger
- 对于冗余字段：命名带 _snapshot 或 _cached（如 seller_name_cached）



### 字段类型的选择

核心原则：> **刚好能覆盖业务范围的最小类型**。在保证数据语义正确的情况下，在存储（空间） + 性能（查询/索引）做权衡。

1. 关于整数类型
能选择小的就选择小的，确定不会出现负数，建议加上无符号，在大数据量的情况下可以极大的减少存储空间。
- **TINYINT**：状态码 (0/1)、年龄、枚举值、布尔值。1字节 / -128 ~ 127 / 0 ~ 255
- `SMALLINT`：端口号、年份、小型计数器、分类ID。2字节 / -32,768 ~ 32,767 / 0 ~ 65,535
- `MEDIUMINT`：较少用，偶尔用于中等规模的自增ID。3字节 / -8,388,608 ~ 8,388,607 / 0 ~ 16,777,215
- **INT** (INTEGER)：用户ID、订单号、时间戳、一般计数（最常用）。4字节 / -21亿 ~ +21亿 / 0 ~ 42亿
- **BIGINT**：雪花算法ID、金融分币值、超大表主键、纳秒级时间戳。8字节 / -922亿亿 ~ +922亿亿 / 0 ~ 1844亿亿


2. 关于字符串类型
`varchar char text`：
- 如果长度固定或者相互之间差异极小，选择char(n)，通常性能更快一些
- 如果长度不固定，选择varchar(n)
- 对于超长文本，选择TEXT

3. 关于小数类型
 `float double decimal`，只要是涉及到钱相关的，需要保证精度不丢失的，选择 `decimal`，如果允许存在误差，追求性能/存储空间的，可以选择`float`（4字节）或者`double` 8字节：
- `decimal`内部是以字符串的形式存储的，存储空间较大，且计算相对慢
- `float double` 内部是直接基于二进制浮点数存储的，计算快，但是会有误差。


3. 关于日期类型
- 如果只需要日期、时间、年份，建议直接选择 `Date`，`TIME`，`YEAR`，因为占用空间小，分别只占3字节和1字节
- 如果同时需要日期和时间，选择`DATETIME`，占8字节





## 存储引擎 
B+树-----页-------行格式

负载对数据的读取和写入，不同的存储引擎有着各自的特性，主要学习了解InnoDB存储引擎。
理解B+树是表的**物理存储结构**，
一张表其实就是一棵B+树，在磁盘上就是一个或者多个文件，那树呢，它是由一个个节点组成的，那在InnoDB里，它这个节点的大小设计为16kb，然后把它称为一页，（那为什么是16kb呢，那肯定是和操作系统有点关心的，毕竟数据库本身是依赖操作系统的文件系统的，可能操作系统读取磁盘上的文件时每次也是16kb吧或者反正肯定和16kb有点关心的，）然后在叶子节点里存储表里的实际每行数据，那这些行数据又是如何组织的呢，这个需要进一步了解页本身的结构组织。


### 页

了解页本身的组织结构，也即由哪些部分组成，每部分的作用。
InnoDB为了不同的目的而设计了不同类型的页，我们把用于存放记录的页叫做`数据页`。

2. 一个数据页可以被大致划分为7个部分，分别是

    - `File Header`，表示页的一些通用信息，占固定的38字节。
    - `Page Header`，表示数据页专有的一些信息，占固定的56个字节。
    - `Infimum + Supremum`，两个虚拟的伪记录，分别表示页中的最小和最大记录，占固定的`26`个字节。
    - `User Records`：真实存储我们插入的记录的部分，大小不固定。
    - `Free Space`：页中尚未使用的部分，大小不确定。
    - `Page Directory`：页中的某些记录相对位置，也就是各个槽在页面中的地址偏移量，大小不固定，插入的记录越多，这个部分占用的空间越多。
    - `File Trailer`：用于检验页是否完整的部分，占用固定的8个字节。
    
3. 每个记录的头信息中都有一个`next_record`属性，从而使页中的所有记录串联成一个`单链表`。

4. `InnoDB`会为把页中的记录划分为若干个组，每个组的最后一个记录的地址偏移量作为一个`槽`，存放在`Page Directory`中，所以在一个页中根据主键查找记录是非常快的，分为两步：

    - 通过二分法确定该记录所在的槽。

    - 通过记录的next_record属性遍历该槽所在的组中的各个记录。

5. 每个数据页的`File Header`部分都有上一个和下一个页的编号，所以所有的数据页会组成一个`双链表`。

6. 为保证从内存中同步到磁盘的页的完整性，在页的首部和尾部都会存储页中数据的校验和和页面最后修改时对应的`LSN`值，如果首部和尾部的校验和和`LSN`值校验不成功的话，就说明同步过程出现了问题。


### 行格式


行格式：知道以下几点即可

1）行格式讲的是一行数数据在一页里是如何组织的，存储的格式是什么，

2）然后对于某行数据很大时可能会溢出在其他页里，所以对于这种数据在查询性能上会有影响

### Buffer Pool
 InnoDB的缓存，在内存中缓存数据、索引、undo页。生产环境通常配置为物理内存的 50%~80%（通过 innodb_buffer_pool_size），可以在运行期间调整，至于它是如何设计的，采用了什么算法我没有深入的去了解，反正不管怎么设计，最后的目的肯定是为了提供命中率吧，尽可能的减少IO。

## 索引

高效获取数据的数据结构。
缺点：
- 创建索引和维护索引要 耗费时间 ，所以会降低增删改操作的性能。
- 占用磁盘空间。

| 索引类型     | 底层数据结构      | 适用查询类型                     | 典型应用场景      |
| -------- | ----------- | -------------------------- | ----------- |
| Normal   | B+ 树        | =, >, <, BETWEEN, ORDER BY | 普通字段加速查询    |
| Unique   | B+ 树（+唯一校验） | 同上 + **唯一性约束**             | 邮箱、用户名等唯一字段 |
| Fulltext | 倒排索引        | 关键词全文搜索（MATCH...AGAINST）   | 文章、评论、描述文本  |
| Spatial  | R 树         | 空间关系（距离、包含、相交等）            | 地图、LBS、GIS  |



聚簇索引的场景下，B+树同时是物理存储结构；而在二级索引场景下，它仅是索引结构。



### B+树索引的设计
首先B+树索引是由页组成的，数据本身是存储在页里面，所以首先**需要快速定位数据在哪一页**，为什么实现这个效果，那么需要为**哪些存储实际数据的页建立一个目录用于快速定位页**，这些页就放在B+树的非叶子节点。

**每层节点都是按照索引列值从小到大的顺序排序而组成了双向链表，而且每个页内的记录（不论是用户记录还是目录项记录）都是按照索引列的值从小到大的顺序而形成了一个单链表**（这样可以通过二分法进行快速定位数据以及范围定位）。如果是`联合索引`的话，则页面和记录按照先按照`联合索引`前边的列排序，如果该列值相同，再按照`联合索引`后边的列排序

### 聚簇索引和非聚簇索引

聚簇索引：指的是使用主键值的大小来构建B+树，然后叶子节点存储完整的记录。这也是InnoDB默认执行的操作，指定来主键，就使用指定的主键，否则会自动生成一个行ID。
而非聚簇索引（二级索引）：是除了主键之外额外创建的索引，它的叶子节点没有存储完整的用户记录，只是额外记录了主键值。

如果要查询的列包含了不是索引的列，那么在二级索引中查找到数据之后，还需要拿着ID去聚簇索引中查找完整的记录，这个过程称为**回表**。二级索引里数据是按照索引值大小顺序排列的，会集中分布在一个或几个数据页中，这个过程称为**顺序IO**，比较快，而在二级索引里拿到的ID可能并不是连续的，那么再去聚簇索引查找时就不是顺序IO（**随机IO**），性能上不够好。

需要回表的记录越多，**使⽤⼆级索引的性能就越低**，甚⾄让某些查询宁愿使⽤全表扫描也不使⽤⼆级索引。⽐⽅说name值在Asa～Barlow之间的⽤户记录数量占全部记录数量90%以上，那么如果
使⽤idx_name_birthday_phone_number索引的话，有90%多的id值需要回表，这不是吃⼒不讨好么，还不如直接去扫描聚簇索引。

那什么时候采⽤全表扫描的⽅式，什么使⽤采⽤⼆级索引 + 回表的⽅式去执⾏查询呢？这个就是查询优化器做的⼯作。



### 联合索引

**同时指定多个列的大小来构建索引**，然后在叶子节点里除了存储主键值，会存储相关的索引列，所以对于经常要查询的列，可以直接构建联合索引来避免回表提高查询性能。

比如指定c2、c3列构建索引：
- 先把各个记录和页按照c2列进行排序。
- 在**记录的c2列相同的情况下，再采用c3列进行排序**，相当于c3列在整个索引结构里其实是无序的，只有c2是有序的，在c2相同的范围里c3才是有序的。所以联合索引的使用必须从最左边的列开始，且连续使用，才能有效利用索引（**最左匹配原则**）。


对于 (a, b, c) 索引，以下查询能用到索引：

| **查询条件**                          | **是否命中索引** | **说明**                               |
| --------------------------------- | ---------- | ------------------------------------ |
| `WHERE a = 1`                     | ✅          | 用到 `a`                               |
| `WHERE a = 1 AND b = 2`           | ✅          | 用到 `a`, `b`                          |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅          | 全部用到                                 |
| `WHERE a = 1 AND c = 3`           | ⚠️ 部分      | 只用到 `a`；因为中间跳过了 `b`，`c` 无法利用索引进行快速定位 |
| `WHERE b = 2`                     | ❌          | 没有从索引的最左列（`a`）开始                     |
| `WHERE b = 2 AND c = 3`           | ❌          | 同上（缺少最左列 `a`）                        |
| `WHERE c = 3`                     | ❌          | 无法使用                                 |

### 最佳实践

<div class="highlight-block highlight-tip">B+树索引的适用条件</div>
- 全值匹配
- 匹配左边的列
- 匹配范围值
- 精确匹配某⼀列并范围匹配另外⼀列
- ⽤于排序
- ⽤于分组


<div class="highlight-block highlight-tip">如何设计索引</div>

- 只为⽤于搜索、排序或分组的列创建索引
- 为列的基数⼤的列创建索引，对于基数比较小的字段，比如表里常见的标记字段，如果经常作为查询条件，建议和其它索引构成联合索引。
- 索引列的类型尽量⼩
- 可以只对字符串值的前缀建⽴索引
- 只有索引列在⽐较表达式中单独出现才可以适⽤索引
- 为了尽可能少的让聚簇索引发⽣⻚⾯分裂和记录移位的情况，建议让主键拥有AUTO_INCREMENT属性。
- 定位并删除表中的重复和冗余索引
- 尽量适⽤覆盖索引进⾏查询，避免回表带来的性能损耗


### 查询
了解查询语句丢给MySQL 时，它的查询方式是什么，有没有走索引，一条查询语句进行语法解析之后就会被交给查询优化器来进行优化，优化的结果就是生成一个所谓的`执行计划`，这个执行计划表明了应该使用哪些索引进行查询，表之间的连接顺序是啥样的，最后会按照执行计划中的步骤调用存储引擎提供的方法来真正的执行查询，并将查询结果返回给用户。

可以通过 `EXPLAIN` 来判断一个SQL它的执行方法是什么，通过查看 `type`字段的值。查询优化器会选择一个代价最小的方法去查询

| type          | 含义                                | 是否使用索引 | 典型 SQL 示例                                                                                                                             | 性能评价  | 优化建议                                 |
| ------------- | --------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------- | ----- | ------------------------------------ |
| `system`      | 表仅有一行（系统表或空表）                     | 是（特殊）  | `SELECT * FROM (VALUES ROW(1)) t;`                                                                                                    | ⭐⭐⭐⭐⭐ | 几乎不会在业务中出现                           |
| `const`       | 通过主键或唯一索引等值查询，最多返回一行              | 是      | `SELECT * FROM users WHERE id = 1;`  <br>`SELECT * FROM users WHERE email = 'a@example.com';`（email 唯一）                               | ⭐⭐⭐⭐⭐ | ✅ 理想状态，无需优化                          |
| `eq_ref`      | JOIN 时，关联列是主键或唯一非空索引，每行精确匹配一行     | 是      | `SELECT u.name, p.bio FROM users u JOIN profile p ON u.id = p.user_id;`（p.user_id 唯一）                                                 | ⭐⭐⭐⭐  | ✅ 一对一关联的最佳方式                         |
| `ref`         | 使用非唯一索引进行等值查询（=），可能返回多行           | 是      | `SELECT * FROM orders WHERE status = 'paid';`（status 有普通索引）  <br>`SELECT * FROM orders WHERE user_id = 1001;`（联合索引 `(user_id, time)`） | ⭐⭐⭐⭐  | ✅ 最常见的高效索引访问                         |
| `fulltext`    | 使用全文索引（FULLTEXT）进行关键词搜索           | 是      | `SELECT * FROM articles WHERE MATCH(title) AGAINST('MySQL');`                                                                         | ⭐⭐⭐   | 🔍 仅用于文本搜索场景                         |
| `ref_or_null` | 类似 `ref`，但额外查找 `NULL` 值           | 是      | `SELECT * FROM orders WHERE user_id = 1001 OR user_id IS NULL;`                                                                       | ⭐⭐⭐   | ⚠️ 避免 `OR ... IS NULL`，可用 `UNION` 替代 |
| `index_merge` | 合并多个索引的结果（交集/并集）                  | 是（多个）  | `SELECT * FROM orders WHERE user_id = 1001 OR status = 'paid';`（user_id 和 status 各有单列索引）                                              | ⭐⭐    | 🚫 不推荐依赖；应改用联合索引                     |
| `range`       | 索引范围扫描（>、<、BETWEEN、IN、LIKE '前缀%'） | 是      | `SELECT * FROM orders WHERE amount > 100;`  <br>`SELECT * FROM users WHERE name LIKE 'Ali%';`                                         | ⭐⭐    | ✅ 可接受；避免 `LIKE '%xxx'`               |
| `index`       | 全索引扫描（遍历整个二级索引）                   | 是（全扫）  | `SELECT user_id FROM orders;`（覆盖索引）  <br>`SELECT * FROM orders ORDER BY user_id;`（无 WHERE）                                            | ⭐     | ⚠️ 无过滤条件时出现；尽量加 WHERE                |
| `ALL`         | 全表扫描（最差）                          | ❌ 否    | `SELECT * FROM orders WHERE description LIKE '%urgent%';`  <br>`SELECT * FROM users WHERE age + 1 = 19;`                              | ❌     | 🚫 必须优化：加索引、改写 SQL                   |

关于连接表的查询，会先选择一个驱动表，查询出符合条件的记录，然后依次遍历每条记录再按照连接条件去查询匹配的数据，所以对于连接条件最后有索引，否则数据量大将是灾难。

被驱动表的连接列必须有索引（如 orders.user_id）；
驱动表的 WHERE 条件尽量走索引，缩小驱动结果集；
被驱动表的 WHERE 条件可通过联合索引优化（如 (user_id, amount)）；
用 EXPLAIN 看两行：确认驱动表、索引使用、rows 数量。


## 事务

> **事务 = 一组操作，要么全部成功，要么全部失败（回滚）**


原子性：事务是最小的执行单元，要么全部成功，要么全部失败，通过**undo log**（回滚日志）来保证（执行了 Insert，回滚时就执行 Delete；执行了 Update，回滚时就执行反向更新）

隔离性：多个并发事务之间相互隔离，互不干扰；通过MVCC（多版本并发控制）+ 锁机制保证。

持久性：只要事务成功提交了，就一定会写入磁盘保存。通过redo log（重做日志）保证，（因为会先写日志，当日志写入成功后才返回事务提交成功，最后再异步更新磁盘的数据）

一致性：指事务执行前后，数据库的数据始终保持完整性，从一个一致的状态转变成另一个一致的状态。通过前面的原子性、隔离性、持久性以及业务逻辑约束共同来保证。


案例：` UPDATE user SET age = 30 WHERE id = 1;`
① 先写 Undo Log：记录旧值：20
② 修改内存（Buffer Pool）：age = 30（内存中）
**③ 写 Redo Log**：记录修改了 age=30
④ 提交事务（commit）关键点：只要 Redo Log 落盘，就算成功
⑤ 异步刷磁盘：慢慢把数据写到磁盘页

在写入磁盘之前，先记录Redo Log  日志，难道Redo Log 日志写入磁盘不慢么？
因为日志写入是顺序IO，直接在末尾追加，相比较把数据写入磁盘页里，是随机IO，需要先定位对应的数据页在哪里，快很多。

### 事务的隔离级别

事务有 隔离性 的特性，理论上在某个事务 对某个数据进行访问 时，其他事务应该进行 排队 ，当该事务提交之后，其他事务才可以继续访问这个数据。也即理论上应该串行访问，但是这样对性能的影响太大 ，所以出现了事务的隔离级别，在保持事务的隔离性和性能之间取得平衡。

<div class="highlight-block highlight-tip"> 先了解下在没有保证多个并发事务的串行执行时会出现哪些问题</div>

- 脏读：事务 A 读取了事务 B 未提交的修改。如果 B 回滚，A 读到的是“不存在”的数据。
- 不可重复读：同一事务内，多次**读取同一行，结果不同**，（因其他事务修改并提交）
- 幻读：同一事务内，多次按相同条件查询，**返回的行数不同**（因其他事务插入/删除）。

<div class="highlight-block highlight-tip"> SQL标准中设置的四种隔离级别</div>

- READ UNCOMMITTED ：读未提交，没有做任何隔离性，所有事务可以直接读取其它未提交事务做的修改。不能避免脏读、不可重复读、幻读等问题。
- READ COMMITTED：读已提交，做了基本的隔离，**一个事务只能读取其它已经提交事务做的修改**(当其它事务还未提交时，读到的还是之前没有的数据；在自己当前事务内可以读取到自己还没有提交的值）。避免了脏读，但是不可避免不可重复读，幻读等问题。
- REPEATABLE READ：可重复读，在一个事务内多次读取同一行，读到的还是原来的内容，避免了脏读、不可重复读，但是幻读问题还存在。MySQL 默认隔离级别。
- SERIALIZABLE：直接串行化，在这个事务期间，禁止其它事务对该表进行更新操作。可以避免所有的并发问题，但是性能很低。

- 读已提交：在当前事务内，只能读取到自己修改的值，其它事务还没提交的值读取不到。
- 可重复读：在自己开启事务的那一刻，如果其它事务还没提交，那自己只能读取到之前到值或者自己修改的值，即使其它事务已经提交了。

**事务的隔离是通过锁+MVCC(多版本）来实现的**，当出现并发问题时，要么通过MVCC解决，要么通过锁来解决，而MySQL的策略是能用 MVCC 就不用锁，只有必要时才加锁。

<div class="highlight-block highlight-tip"> Read Uncommitted 读未提交</div>
基本不会用，了解即可，在这种隔离级别下几乎不用任何锁也不用MVCC，什么脏数据都能读到。


<div class="highlight-block highlight-tip"> Read Committed 读已提交</div>
查询时：SELECT，用MVCC。
修改时：UPDATE/DELETE 加行锁。（效果：当一个事务对某条数据修改后，还没有提交事务，其它事务无法再去修改这条数据，会等待直到等待超时或者另外一个事务提交释放了锁。）


<div class="highlight-block highlight-tip"> Repeatable Read 可重复读</div>
查询时：MVCC
修改：行锁 + Next-key Lock

### 锁与MVCC实现

读：用MVCC
写：用锁

```sql
并发控制

├── MVCC（不加锁，解决读问题）
│     └── 快、并发高
│
└── 锁（Lock，解决写冲突）
      └── 慢、但强一致
```

<div class="highlight-block highlight-tip">锁的分类</div>
1、按照用途
- 共享锁（S锁）：`SELECT ... LOCK IN SHARE MODE;`  在这条语句所在事务还没提交之前
	- 其它事务**可以普通读，也可以加共享锁读**
	- 不能写，会阻塞X锁，也即其它事务如果使用了  `SELECT ... FOR UPDATE;` 也会被阻塞。
- 排他锁（X锁）：其**它事务只能普通读**，不能共享锁读或者再次加排他锁进行读/写操作。
	- 手动加：`SELECT ... FOR UPDATE;`  
	- 在隔离级别下更新操作会自动加：`UPDATE / DELETE（自动）`

`LOCK IN SHARE MODE `很少用，因为容易发生死锁，除非明确需要“多人同时读但禁止写”。
```sql
Session A:
 SELECT * FROM t WHERE id=1 LOCK IN SHARE MODE; 
-- 想 UPDATE，但需要 X 锁 
Session B: 
SELECT * FROM t WHERE id=1 LOCK IN SHARE MODE; 
-- 也想 UPDATE，也需要 X 锁
 → A 等 B 释放 S 锁，B 等 A 释放 S 锁 → **死锁！**
```
**FOR UPDATE（排他锁）：取后要更新，防止其他事务干扰（最常用！），保证原子性**
```SQL
-- 下单扣库存
START TRANSACTION;
SELECT stock FROM products WHERE id = 100 FOR UPDATE;  -- 锁住
IF stock > 0 THEN
    UPDATE products SET stock = stock - 1 WHERE id = 100;
    INSERT INTO orders (...) VALUES (...);
END IF;
COMMIT;
```

2、按照范围：
- Record Lock（记录锁）：锁一条记录
- Gap Lock(间隙锁)：锁区间，不锁数据，防止插入
- Next-key Lock(临键锁)：记录锁 + 间隙锁。> RR 隔离级别下默认使用 Next-Key Lock 防止幻读
>MySQL中在RR隔离级别下，普通的读还是存在幻读问题的，只有通过for update加锁读，mysql会使用Next-key Lock来避免幻读问题

<div class="highlight-block highlight-tip">锁的工作原理</div>

锁是加在“索引”上的，不是行本身 ，
`UPDATE user SET age = 30 WHERE id = 10;`
1. 走索引（id）
2. 在索引记录上加锁（如果是范围查询时，则会锁符合范围内的所有记录）
如果没有走索引，**全表扫描 → 锁整表** ，所以我们在更新时，尽量走索引更新
### 使用事务


```SQL
-- 开启事务
START TRANSACTION;
-- 或简写为：
BEGIN;

-- 执行一系列 SQL 操作（INSERT / UPDATE / DELETE 等）
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;

```

### EXPLAIN 查看执行计划

在SQL语句之前加上 `EXPLAIN` 来查看这条SQL语句的执行计划，通过得到的执行计划来判断这个SQL语句是否走了索引。

`EXPLAIN  SELECT * FROM t_user WHERE nickname='王燕'`

下面是输出的字段说明：

| 字段        | 含义          | 如何判断是否走索引                                                                                        |
| --------- | ----------- | ------------------------------------------------------------------------------------------------ |
| `type`    | 访问类型        | `ref` / `range` / `const` / `index` 表示用了索引；`ALL` 表示全表扫描 ❌                                        |
| `key`     | 实际使用的索引名    | 如果为 `NULL`，说明没走索引 ❌                                                                              |
| `key_len` | 使用的索引长度（字节） | 值越大，通常表示用到了更多列（可辅助判断联合索引用了几列）                                                                    |
| `rows`    | 预估扫描行数      | 数值越小越好；如果接近总行数，可能没走有效索引                                                                          |
| `Extra`   | 额外信息        | 出现 `Using index` 表示覆盖索引（高效）✅；出现 `Using where` 可能回表；出现 `Using filesort` 或 `Using temporary` 通常性能差 |
### 性能监控-Performance Schema
MySQL 的 **Performance Schema (P_S)** 是一个用于监控 MySQL Server 运行时的底层特性的工具。简单来说，记录了数据库运行过程中的每一处细节：从 SQL 执行到锁竞争，从文件 I/O 到内存消耗。

Performance Schema 的设计目标是**低延迟**和**不破坏服务可用性**。它主要由两个核心概念组成：
1. **Instruments（检测点/仪表）：** 埋在源码里的探测点。比如，每当发生“打开一个文件”的操作时，对应的检测点就会触发。
2. **Consumers（消费者）：** 存储检测点产生数据的地方。它们通常表现为 `performance_schema` 数据库里的各种表。
    
运作流程：**当代码运行到某个 Instrument 时，它会收集数据（比如消耗了多少微秒），然后将这些数据存入相关的 Consumer 表中。**

默认是开启的，检查开启状态：
```SQL
SHOW VARIABLES LIKE 'performance_schema';
```

手动查询 `performance_schema` 的表名太长且单位（皮秒）难以阅读。为此，MySQL 官方提供了一个 **`sys` schema**，它通过视图（View）封装了 Performance Schema 的数据。

**在实际工作中，我们 90% 的情况是直接查 `sys` 库：**

- **查看最耗时的 SQL：** `SELECT * FROM sys.statement_analysis;`

- **查看库中冗余/无用的索引：** `SELECT * FROM sys.schema_unused_indexes;`
    
- **查看表锁等待情况：** `SELECT * FROM sys.innodb_lock_waits;`
