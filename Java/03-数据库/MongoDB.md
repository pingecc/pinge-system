# 为什么MongoDB可以作为缓存

它能作为缓存，是因为：

1. **相对速度优势**：比原始数据源（SQL/外部接口）快得多。
2. **内存机制**：热点数据实际驻留在内存中。
3. **功能匹配**：TTL 索引提供了缓存所需的过期机制。
4. **场景特化**：适合**结构复杂、需持久化兜底、并发量中等**的缓存场景。

传统的缓存系统（如 Redis）确实主要依赖内存来实现微秒级的极速响应，而 MongoDB 默认是磁盘持久化的数据库。

那么，为什么业界仍然有人（或在特定场景下）把 MongoDB 当作缓存用？这主要基于以下几个**核心逻辑的转换**：

 1. “缓存”的定义不仅仅是“纯内存”

在架构设计中，“缓存”的核心定义是：位于数据源（如关系型数据库、外部 API）和应用之间，用于存储“计算结果”或“热点数据”，以减少对原始数据源的访问压力。**所以只要比从数据源获取数据或者可以减少数据源的压力，就可以被当作缓存。

- 传统缓存 (Redis)：目标是速度极致。数据主要在内存，重启可能丢失（除非配置持久化），适合存会话、计数器、临时列表。
- MongoDB 作为缓存：目标是**减轻主库压力 + 数据结构灵活**。它虽然落盘，但只要它的读取速度比你的“原始数据源”（比如复杂的 SQL 联表查询、慢速的外部 API）快，它就在发挥“缓存”的作用。

 2. MongoDB 其实大量使用了内存 (WiredTiger 引擎)

虽然 MongoDB 是磁盘数据库，但现代版本的默认存储引擎 **WiredTiger** 拥有非常强大的内存管理机制：

- 内部缓存 (Internal Cache)：WiredTiger 会默认使用物理内存的 50%（可配置）作为内部缓存池。
- 热数据驻留：如果你的缓存数据集大小（Working Set）小于这个内存池，**热点数据实际上是完全在内存中运行的**，读写性能非常接近纯内存数据库。
- **操作系统页缓存**：即使超出了内部缓存，操作系统的文件系统缓存（Page Cache）也会尽量将频繁读取的磁盘块保留在内存中。

**结论**：只要你的缓存数据量控制在内存范围内，MongoDB 的读取延迟通常在 **亚毫秒到几毫秒** 级别。对于很多业务场景（如避免一次耗时 200ms 的复杂 SQL 查询），几毫秒的读取完全是可以接受的“缓存加速”。

3. 利用 TTL 索引实现“自动过期”

这是 MongoDB 能做缓存的关键功能。你可以给集合创建一个 `TTL Index` (Time To Live)：

```javascript
// 创建索引，文档在 createdAt 字段时间过去 3600 秒后自动删除
db.cache_collection.createIndex({ "createdAt": 1 }, { expireAfterSeconds: 3600 });
```

这使得 MongoDB 能够像 Redis 一样，**自动清理过期的缓存数据**，无需应用层编写复杂的清理逻辑。

 4. 独特的优势场景：复杂结构 + 持久化需求

这是 Redis 很难做到的，却是 MongoDB 的强项：

- **复杂数据结构**：Redis 的 String/Hash/List 处理深度嵌套的 JSON 对象比较麻烦（通常需要序列化/反序列化）。MongoDB 原生就是 BSON（类似 JSON），存取复杂对象极其方便。
- **“缓存即备份”**：在某些场景下，你希望数据即使过期了也不要立刻彻底消失（或者希望缓存失效后数据依然可查）。用 Redis 做缓存，一旦内存满了被淘汰或重启，数据就没了；用 MongoDB，数据虽然从“缓存层”逻辑上失效了，但物理上还在磁盘里，可以作为历史数据追溯。

 5. 什么时候**绝对不要**用 MongoDB 做缓存？

尽管有上述理由，但如果你的场景符合以下特征，**必须**用 Redis/Memcached，不能用 MongoDB：

1. **超高并发 (QPS > 10万+)**：MongoDB 的单节点写入/读取瓶颈远低于 Redis。
2. **极低延迟要求 (< 1ms)**：网络开销 + 磁盘协议开销会让 MongoDB 很难稳定在 1ms 以内，而 Redis 轻松做到。
3. **纯临时数据**：数据丢了也无所谓，且数据量巨大远超内存（如短信验证码、短期会话），用磁盘存这些是浪费 IO。
4. **需要高级缓存算法**：如严格的 LRU/LFU 淘汰策略，Redis 原生支持，MongoDB 主要靠 TTL。


# 应用场景
数据是“以对象为中心”（一个请求主要操作一个大对象），且这个对象的结构经常变，或者数据量大到单机存不下，那么 MongoDB 是绝佳选择。
存商品详情、订单快照、用户行为日志、内容数据（灵活、海量）。
