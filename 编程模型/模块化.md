




首先，编程语言的模块化就是在一个代码文件里面可以去访问另外一个代码文件里面的代码，这就牵扯到两个最基本的问题，假设我现在需要在文件 A 里面去访问文件 B 里面的代码在文件里面，我该如何去声明我要访问文件 B 中的代码，**如何声明我要使用哪个模块**，第二编辑器或者说是解释器，他又该如何根据我的声明去找到文件B中的代码，也即**如何加载目标模块，使能够正确的访问。对于一门编程语言的模块化设计而言，通常可能会有包的概念，包就是把模块进一步的进行分类管理**，而对于声明模块者而言，编程语言通常还会提供一些语法来进一步设计这个模块该如何被访问。


| **问题**        | **解决方案**                             |
| ------------- | ------------------------------------ |
| 我如何声明要使用哪个模块？ | `import`、`using`、`require` 等语法       |
| 如何找到这个模块？     | 模块加载器（搜索路径、classpath、node_modules 等） |
| 如何组织大量模块？     | Package、Namespace、Module             |
| 模块哪些内容允许别人访问？ | `public`、`export`、可见性规则等             |

# 模块于文件系统

> 问：几乎所有的编程语言里，一个模块就是一个单独的文件，为什么要起模块化这个词？

## ⁠1 ⁠代码组织
把代码分到不同的文件里，仅仅是**物理层面**的拆分；而“模块化”（Modularization）是一个**逻辑层面**的工程设计概念。

如果只是随手把一万行代码平均切成十个文件，互相之间依然各种乱调、共享全局变量，那只能叫“文件拆分”，绝不能叫“模块化”。之所以要专门起“模块化”这个词，是因为它不仅关乎代码存放的位置，更关乎代码的**组织原则**：

- **划分边界与信息隐藏（封装）：** 一个真正的模块有明确的边界。它要求开发者思考：哪些核心逻辑是私有的（Internal），哪些接口是公开给别人用的（API）。文件本身没有这个约束，但模块化思维强制你建立这种“黑盒”机制，外部使用者不需要也不应该知道黑盒里面是怎么运作的。
- **高内聚与低耦合：** 模块化要求把逻辑高度相关的功能聚集在同一个模块里（高内聚），同时尽量减少不同模块之间的依赖和互相影响（低耦合）。如果你修改了一个文件里的代码，导致另外五个文件报错，这就说明代码没有真正被模块化。
- **命名空间隔离：** 在没有模块化概念的时代（比如早期的 JavaScript，所有的脚本直接在 HTML 里引入），所有的变量全在全局作用域里，极其容易发生命名冲突。模块化赋予了每个文件独立的命名空间（Namespace），彻底解决了“变量名打架”的问题。  
    
- **可替换与复用：** “模块”这个词借用于工业制造（比如电脑的内存条、汽车的轮胎）。模块化的最终目的是让代码像乐高积木一样，具有独立性和通用性。当你需要升级支付功能时，可以直接把旧的支付模块拔下来，插上新的，而不需要重写整个系统。


简单来说，**文件是代码的容器，而模块是功能的单位**。文件系统决定了代码存在哪里，模块化决定了代码如何互相协作而不至于走向崩溃。

## ⁠2 ⁠模块与文件的对应关系

虽然在 Python 或 JavaScript 等非常流行的语言中，“一个文件就是一个模块”几乎是标准做法，但在整个编程语言的世界里，**“模块”（Module）和“文件”（File）并没有绝对的对应关系**。

  

我们可以把主流编程语言按“模块与文件”的关系分为三大类：

  

**1. 一文件 = 一模块（以文件为物理边界）**
- **代表语言：** Python、JavaScript (Node.js/ES6)、Ruby。
- **特点：** 语言设计者直接利用了操作系统的文件系统来作为代码的隔离边界。你新建一个 `.py` 或 `.js` 文件，它天然就是一个拥有独立作用域的模块。
    
**2. 多文件 = 一模块（模块比文件大得多）**
- **代表语言：** Go、Java、C#。
- **特点：** 在这些语言里，一个单独的文件通常被称为“类”或“文件”，而“模块”是一个宏大的工程级概念，包含了成百上千个文件。  
    - **Go：** 一个 Go Module（由 `go.mod` 定义）是一个完整的项目，里面包含多个 Package（包，即文件夹），每个 Package 里面又有多个 `.go` 文件。  
    - **Java：** 从 Java 9 开始引入的 JPMS（Java 模块系统），一个 Module 是由多个 Package（包）组成的集合，跨越了无数个 `.java` 文件。
    - **C#：** 它的物理模块单位通常是程序集（Assembly，即 `.dll` 或 `.exe` 文件），这往往是由几十上百个源文件编译而成的。
        
          
    
**3. 一文件 = 多模块（模块比文件小）**

- **代表语言：** Rust、C++。
- **特点：** 模块完全是代码级别的逻辑概念，和文件怎么存没关系。  
    - **Rust：** 你完全可以在同一个 `.rs` 文件里，用 `mod A { ... }` 和 `mod B { ... }` 写出多个互相隔离的模块。   
    - **C++：** 同样支持在一个物理文件里定义多个不同的命名空间（Namespace）或在 C++20 中定义不同的模块分区（Module Partitions）。
        
          
        

**总结：** “文件”是操作系统用来存储硬盘数据的机制，**而“模块”是编译器或解释器用来管理作用域、依赖和封装的机制。** 恰好有些语言把这两者画了等号，但在更底层的系统级语言或更大型的企业级语言中，模块往往超越了单个文件的范畴。
# 声明

假设现在有2个文件，现在需要在A.py中调用B.py中的函数

```
project/
├── A.py
└── B.py
```

其中 `B.py` 中有一些代码。

```python
# B.py

def hello():
    print("Hello")
```

现在，我希望在 `A.py` 中调用它。

```python
# A.py

hello()
```

解释器看到这里，第一个问题就是：hello 是哪里来的？因此，模块化首先需要解决第一个问题：**我要告诉编译器（解释器），我要使用哪个模块**。这就是声明（Declaration）。每个语言都有一套自己的声明语法。

1）python的声明
```python
import B

B.hello()
```

2）Java的声明
```java
import com.demo.utils.StringUtils;
```

# 加载

有了声明之后，编译器或者接收器就需要根据声明来找到对应的模块，这就是模块加载。
```
根据声明
↓
定位文件
↓
读取文件
↓
执行文件
↓
建立模块对象
↓
提供给 A 使用
```

不同语言的寻找方式也不同：
1）python
```
当前目录
↓
PYTHONPATH
↓
site-packages
↓
标准库
```

2）Java
```
当前目录
↓
PYTHONPATH
↓
site-packages
↓
标准库
```

# 包

随着模块越来越多，很容易出现命名冲突，于是就会引入一个新的概念：包。 用于对模块进行分类管理。

```
project/
erp/
    order.py
    user.py
crm/
    customer.py
    user.py
```
