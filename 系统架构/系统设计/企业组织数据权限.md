
要对一个系统做数据权限，简单直观的讲其实就是确定2件事：
1）系统中**哪些页面（资源）的数据需要做数据权限**
2）针对需要做数据权限的页面，对应的**隔离范围**是什么

# 数据权限规则核心设计

通过绑「角色 + 隔离范围」实现灵活的数据权限，提供以下隔离规则：
- 所有：所有人都可见，默认值，只要拥有该页面功能权限，就可以看到全部数据。
- 部门：只能看到自己部门以及子部门的数据，其它部门的数据不可见。
- 权限人：只有对应数据的权限人是自己时才可见，关于权限人的概念后文细讲。

下面详细讲解不同隔离范围的应用场景以及效果。

## 数据隔离范围规则

### 所有

默认值，数据不做任何隔离，只要拥有该页面功能菜单权限，就可以看到所有数据。
>更严谨的说法，只能看到自己公司的全部数据，对于需要做租户隔离的系统，默认认为其已经做了租户隔离。

### 部门

当勾选了该规则时，用户只能看到自己部门以及子部门下的数据，其它部门的数据不可见。


### 权限人

【权限人】指的是对应**数据负责人集合**，默认情况下可以**理解成所有单据的创建人都是权限人**。如果设置了隔离范围规则是权限人时，只有对应的权限人是当前用户时，才可见，也即对于大家只能看见自己创建的数据。


另外【权限人】提供扩展授权，通过扩展用户，扩展部门来实现数据的**共享**。

场景1：**不仅仅是创建人可见，可以是多个负责人可见。**
比如下面是大货系统的客户页面，可以看到在创建客户时需要指定客户负责人，业务负责人，财务负责人，那么就可以指定这些负责人都是客户列表的【权限人】，当设置隔离规则为权限人时，对应的客户负责人。财务负责人，业务负责人都可以看到。
![[Pasted image 20260613231449.png]]
>如果存在这样的需求，一个页面的权限人字段不是创建人时，是其它字段时，需要提前告知，后端写死来实现，不考虑通过前端配置可以动态指定权限人字段是什么，过于复杂且有性能问题。


场景2：**进一步的共享数据，添加其它用户或者部门来实现权限的继承。**
在【权限人】规则下，默认情况下只有当权限人是本人时才可见，但是我们可以
1）添加其它用户，这样拥有该角色的用户不仅可以看到权限人是自己的数据，还可以看到权限人是其它用户的数据。
2）添加其它部门，这样拥有该角色的用户不仅可以看到权限是自己的数据，还可以看到权限人是其它部门下所有用户的数据。


## 需求实现

下面展示不同数据权限需求下，如何通过这套规则来完成数据的隔离和共享。


### 不同部门之间数据相互隔离不可见

需求：不同部门之间数据相互隔离不可见，用户只能看到自己部门的数据。

1）确定系统中哪些页面需要做这样的数据隔离

2）找到拥有这些页面菜单权限的所有角色

3）依次在这些角色上给对应的页面资源配置数据权限规则：部门


### 用户只能看到自己负责的数据

需求：每个业务以及财务人员需要看到自己负责的客户数据

1）找到拥有客户列表权限的所有角色

2）依次在这些角色上给对应的页面资源配置数据权限规则：权限人


### 用户只能看到自己负责的数据，但是部门领导人需要看到部门所有数据

需求：每个业务以及财务人员只能看到自己负责的客户数据，但是业务主管需要可以看到自己部门所有负责的客户数据
1）找到拥有客户列表权限的所有角色

2）依次在这些角色上给对应的页面资源配置数据权限规则：权限人

3）再创建一个角色：业务主管，给业务主管添加客户列表功能权限

4）再给业务主管角色设置数据权限规则：权限人，同时将其部门下的所有用户进行添加。这样业务主管就可以看到权限人是自己部门所有人的数据

>或者另外一种实现，给业务主管角色直接设置权限规则：部门。同样可以业务主管看到自己部门下的所有数据

### 若一个用户存在多个角色，每个角色的数据权限设置不一样的情况是如何处理的？

1）按照**优先级进行处理**，全部可见优先于部门可见，部门可见优先于权限人可见。
2）**对于权限人规则，取并集**。

案例1：用户同时拥有角色A和角色B，针对客户列表，在角色A中设置的权限规则：所有人，在角色B中设置设置的权限规则：部门
则：用户在客户列表的数据权限为：所有人

案例2：针对客户列表，老王同时拥有客户维护角色和部门主管角色，在客户维护角色中设置的权限规则为：权限人，但权限人仅本人可见。在部门主管角色中设置的权限规则：权限人，同时扩展添加了部门A下的所有用户。
则：老王在客户列表的数据权限为：权限人为自己以及部门A下的所有用户

### 总结

针对需要“共享” 的数据，比如负责人需要看到自己部门的所有数据，或者其它部门的数据，或者财务部门需要看到其它部门的数据，创建一个角色，设置权限规则为：权限人，然后把需要共享的人或者部门的数据添加到该角色即可。




## 核心表结构设计

```text
用户(User)
    ↓
角色(Role)
    ↓
资源(Resource)
    ↓
数据权限(DataScope)
    ALL
    DEPT
    OWNER
    ↓
扩展授权
    用户
    部门
    ↓
业务数据权限人
```


### 数据资源表

在一开始就提到了首先就是要确定系统中的哪些页面需要做数据权限，但是同一份数据可能会有多个入口，比如客户数据，可能来自：客户列表页面、客户导出、客户统计页面。
但是本质上都是：Customer，为了保持统一，这里抽象成 资源。这样前端无论是客户列表查询还是客户导出，都应用同一套规则。

 **sys_data_resource**

```sql
CREATE TABLE sys_data_resource
(
    id BIGINT PRIMARY KEY,
    resource_code VARCHAR(50) NOT NULL,
    resource_name VARCHAR(100) NOT NULL,
    remark VARCHAR(500),
    create_time DATETIME,
    update_time DATETIME,
    UNIQUE(resource_code)
);
```

### 角色数据权限表

 **sys_role_data_permission**

```sql
CREATE TABLE sys_role_data_permission
(
    id BIGINT PRIMARY KEY,
    role_id BIGINT NOT NULL,
    resource_code VARCHAR(50) NOT NULL,
    scope_type VARCHAR(20) NOT NULL,
);
```

其中`scope_type`取值：
- `ALL`：全部
- `DEPT`：部门
- `OWNER`：权限人

示例：

| **role** | **resource** | **scope** |
| -------- | ------------ | --------- |
| 销售员      | CUSTOMER     | OWNER     |
| 销售员      | ORDER        | OWNER     |
| 销售主管     | CUSTOMER     | DEPT      |
| 财务经理     | CUSTOMER     | ALL       |


### 扩展授权用户表

【权限人】规则下的额外授权用户

```sql
CREATE TABLE sys_role_data_permission_user
(
    id BIGINT PRIMARY KEY,
    permission_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL
);
```
> 上面的permission_id 是sys_role_data_permission表的Id

### 扩展授权部门表

【权限人】规则下的额外授权部门

```sql
CREATE TABLE sys_role_data_permission_dept
(
    id BIGINT PRIMARY KEY,
    permission_id BIGINT NOT NULL,
    dept_id BIGINT NOT NULL
);
```

> 上面的permission_id 是sys_role_data_permission表的Id


### 设计目标

解决两个问题：
```text
1. 哪些资源需要数据权限
2. 当前用户能看到哪些数据
```

### 核心设计思想

 **数据权限 = 资源 + 数据范围**

```text
角色
    ↓
资源(Resource)
    ↓
数据范围(DataScope)
```


例如：针对客户资源(CUSTOMER) 和 订单资源（ORDER），不同的角色设置不同的数据范围

```text
[销售员]
CUSTOMER -> OWNER
ORDER -> OWNER

[销售主管]
CUSTOMER -> DEPT
ORDER -> DEPT

[总经理]
CUSTOMER -> ALL
ORDER -> ALL
```

### DataScopeType

权限范围枚举类：

```java
public enum DataScopeType {
    /**
     * 所有数据
     */
    ALL,
    /**
     * 当前部门及子部门
     */
    DEPT,
    /**
     * 权限人
     */
    OWNER
}
```



### DataPermission

数据权限注解：
```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataPermission {

    String resource();
}
```


对于未来可能需要做数据权限的资源在查询方法添加该注解：
```java
@DataPermission(resource = "CUSTOMER")
public Page<CustomerVO> page(CustomerQuery query)
{
    return customerMapper.page(query);
}
```


### DataPermissionRule

权限计算后的结果类：用于存储当前用户针对某个资源拥有的权限规则

```java
@Data
public class DataPermissionRule {

    /**
     * 数据范围
     */
    private DataScopeType scopeType;

    /**
     * 可见用户
     */
    private Set<Long> userIds;

    /**
     * 可见部门
     */
    private Set<Long> deptIds;
}
```

例如：
```java
{
    scopeType: OWNER,
    userIds: [
        张三,
        李四,
        王五
    ]
}
```

### DataPermissionAspect

```java
@Aspect
@Component
@RequiredArgsConstructor
public class DataPermissionAspect {

    private final DataPermissionService dataPermissionService;

    @Around("@annotation(dataPermission)")
    public Object around(
            ProceedingJoinPoint joinPoint,
            DataPermission dataPermission) throws Throwable {
        try {
			// 获取对应的资源code
            String resourceCode =
                    dataPermission.resource();
			// 获取当前登录用户
            LoginUser loginUser =
                    SecurityUtils.getLoginUser();
			// 根据当前用户和资源code计算得到对应的权限
            DataPermissionRule rule =
                    dataPermissionService.buildRule(
                            loginUser.getUserId(),
                            resourceCode);
			// 将得到的权限设置到当前上下文，后续在mybatis插件里获取拼接SQL
            DataPermissionContext context =
                    new DataPermissionContext();
            context.setResourceCode(resourceCode);
            context.setRule(rule);
            DataPermissionHolder.set(context);
            return joinPoint.proceed();

        } finally {
            DataPermissionHolder.clear();
        }
    }
}
```

### DataPermissionService

权限规则构建服务：

```java
@Service
@RequiredArgsConstructor
public class DataPermissionService {

    private final SysRoleDataPermissionMapper mapper;
    private final DeptService deptService;

    public DataPermissionRule buildRule(
            Long userId,
            String resourceCode) {
        // 用户可能绑定多个角色，多个角色对于该资源都设置了权限，这里取优先级最大的权限规则
        DataScopeType scopeType =
                queryMaxScope(userId, resourceCode);

        DataPermissionRule rule =
                new DataPermissionRule();

        rule.setScopeType(scopeType);

        switch (scopeType) {
            case ALL:
                break;
            case OWNER:
                rule.setUserIds(
                        buildOwnerUsers(userId,
                                resourceCode));
                break;
            case DEPT:
                Long deptId =
                        SecurityUtils.getDeptId();
                Set<Long> deptIds =
                        deptService
                                .findSelfAndChildren(
                                        deptId);
                rule.setDeptIds(deptIds);
                break;
        }
        return rule;
    }
}
```



### ResourcePermissionHandler

资源权限处理器：

```java 
public interface ResourcePermissionHandler {
    /**
     * 资源编码
     */
    String resourceCode();
    /**
     * 构建SQL权限条件
     */
    PermissionCondition buildCondition(
            DataPermissionRule rule);
}
```

对于未来所有可能需要做数据权限的资源，都需要实现该接口。

案例1：订单资源未来需要做数据权限，则新增一个订单权限Handler

```java
@Component
public class OrderPermissionHandler
        implements ResourcePermissionHandler {

    @Override
    public String resourceCode() {
        return "ORDER";
    }

    @Override
    public PermissionCondition buildCondition(
            DataPermissionRule rule) {

        switch (rule.getScopeType()) {
            case ALL:
                return PermissionCondition.empty();
            case OWNER:
				// 假设订单的权限人字段是 create_by
                return PermissionCondition.of(
                        "create_by in ({0})",
                        rule.getUserIds()
                );
            case DEPT:
                return PermissionCondition.of(
                        "dept_id in ({0})",
                        rule.getDeptIds()
                );
            default:
                return PermissionCondition.empty();
        }
    }
}
```



### PermissionCondition

SQL条件对象

```java
@Data
@AllArgsConstructor
public class PermissionCondition {

    /**
     * SQL片段
     */
    private String sql;

    /**
     * 参数
     */
    private List<Object> params;

    public static PermissionCondition empty() {
        return new PermissionCondition(null, List.of());
    }
}
```




### DataPermissionContext

权限上下文：

```java
public class DataPermissionContext {

    private static final ThreadLocal<PermissionCondition> HOLDER
            = new ThreadLocal<>();

    public static void set(
            PermissionCondition condition) {

        HOLDER.set(condition);
    }

    public static PermissionCondition get() {

        return HOLDER.get();
    }

    public static void clear() {

        HOLDER.remove();
    }
}
```
