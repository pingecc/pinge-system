

| 概念                              | 核心定位 | 解决什么问题              | 类比                     |
| ------------------------------- | ---- | ------------------- | ---------------------- |
| **Agent（智能体）**                  | 主体   | 自主理解目标、规划、决策、循环执行   | 数字员工 / 项目负责人           |
| **MCP（Model Context Protocol）** | 连接协议 | 标准化“如何连接外部工具和数据”    | USB-C 接口 / 万能转接头       |
| **Skill（技能）**                   | 能力模块 | 封装“如何做某类任务”的专业方法和流程 | **技能手册 / SOP / 专项工具包** |

### 1. Agent：真正的“干活主体”
Agent 是以大模型为大脑，加上记忆、规划、工具调用和循环机制的**自主系统**。  
你给它一个目标，它自己决定下一步做什么、用什么工具、怎么调整。

没有 Agent，MCP 和 Skill 都只是“能力”或“接口”，没有自主执行者。

### 2. MCP：让 Agent 能“连上”外部世界
**MCP（Model Context Protocol）** 是 Anthropic 提出、后来成为开放标准的协议（目前已捐给 Linux 基金会相关组织）。

- 核心作用：标准化 Agent 与外部工具、数据源、API 的连接方式。
- 被广泛称为 **“AI 的 USB-C”**。
- 架构：MCP Server 暴露工具（Tools）、资源（Resources）、提示（Prompts）；Agent（Host）通过 MCP Client 发现并调用它们。
- 好处：不用为每个工具单独写集成代码，一次接入，多处复用。

**MCP 解决的是“连不连得上”的问题**（管道通不通）。

### 3. Skill：让 Agent “知道怎么用”
**Skill** 是更高层的能力封装。

- 通常是可复用的模块（很多实现是 `SKILL.md` 这类自然语言描述的文件）。
- 内容包括：任务目标、执行步骤、依赖工具、规则约束、验收标准、失败处理等。
- 它教 Agent “遇到这类任务时，按这个专业方法来做”。
- Skill 可以被 Agent 动态选择调用，也可以被固定的 Workflow 调用。

**Skill 解决的是“用得好不好”的问题**（有工具之后，知道怎么正确、高效地用）。

### 三者如何配合（最常见的组合）

```
用户目标
    ↓
Agent（大脑：规划、决策、循环）
    ↓
加载相关 Skill（专业方法论）
    ↓
通过 MCP 调用外部工具 / 数据（实际执行）
    ↓
观察结果 → 继续规划 / 调整 → 直到完成
```

**简单例子**：  
你让 Agent “做竞品分析报告”。

1. Agent 理解目标并开始规划。
2. 加载“竞品分析 Skill”（知道要看哪些维度、报告结构、评估标准）。
3. 通过 MCP 调用搜索工具、网页抓取工具、文档生成工具等。
4. 根据 Skill 的指导整理结果，迭代完善，最终输出报告。

### 一句话总结它们的关系

- **Agent** = 会思考、会决策的执行者  
- **MCP** = 标准化的“手”（连接外部能力的协议）  
- **Skill** = 专业“肌肉记忆 / 操作手册”（教它怎么用这些手完成特定工作）

没有 MCP，Agent 很难方便地接各种工具；没有 Skill，Agent 即使有工具也容易“乱用力”；没有 Agent，MCP 和 Skill 只是静静躺着的能力，无法自主完成复杂目标。

当前主流实践正是把这三者组合起来构建生产级 AI 应用：用 MCP 解决连接问题，用 Skill 沉淀领域经验，用 Agent 负责自主推进。


# 关于提示词和SKill
- 如果你只是把一段好用的提示词保存成文件，再手动塞给模型 → 这更接近**封装提示词**。
- 如果这份文件被系统识别为可安装、可发现、可自动加载的“能力单元”，并且明确声明了工具、流程、规则 → 这就是 **Skill**。

Anthropic 等官方表述也把它定位为 **procedural knowledge**（程序性知识）：教模型“如何完成特定任务或工作流”，而不仅仅是“用什么语气说话”。

**一句话**：Skill 常常以提示词的形式呈现，但它是**结构化的、可复用的能力封装**，比单纯的提示词多了流程、工具绑定、规则和可管理性。提示词是它的常见载体，但不是它的全部。


# Harness

### 一句话定义
**Agent = Model + Harness**

- **Model（模型）**：负责思考、推理、决策的“大脑”。
- **Harness（线束）**：包裹在模型外面的所有软件基础设施，让模型能真正“行动起来”。

没有 Harness，大模型只是文本生成器；有了 Harness，它才能变成能多步执行、调用工具、记住状态、受控行动的真正 Agent。

### 为什么叫 “Harness”？
原意是“马具 / 线束”——给马套上缰绳、鞍具，才能安全、有效地使用它的力量。  
同理，Harness 把模型的原始能力“套”起来，让它在真实环境中可控、可靠地工作。

社区流行的说法是：  
> **如果你不是模型，那你就是 Harness。**

### Harness 通常包含什么？

常见组件包括：

| 组件 | 作用 |
|------|------|
| **循环引擎（Loop）** | 驱动“思考 → 行动 → 观察 → 再思考”的循环，直到任务完成 |
| **工具调度** | 真正执行模型发出的工具调用（API、代码、文件、MCP 等） |
| **状态与记忆** | 管理会话历史、长期记忆、进度记录，而不是全塞进上下文窗口 |
| **上下文管理** | 压缩、筛选、注入关键信息，避免窗口溢出 |
| **沙箱 / 工作区** | 隔离的执行环境（文件系统、终端、浏览器等） |
| **护栏与权限** | 审批策略、作用域权限、安全边界、监控与审计 |
| **错误恢复与钩子** | 重试、补偿、中间件、生命周期管理 |

微软、DeepSeek 等官方定义也类似：Harness 是把语言模型变成能干活的 Agent 的**运行时脚手架**。

### 和相关概念的区别

- **Framework（框架）**（如 LangGraph、CrewAI）：提供构建块和工具库，用来*搭建* Harness。
- **Scaffolding（脚手架）**：有时指模型“看得到”的部分（提示词、工具描述），Harness 更强调真正驱动运行的循环与执行层。日常讨论中常把两者合称为 Harness。
- **Skill / MCP**：是 Harness 内部可插拔的能力模块和连接协议，属于 Harness 的组成部分，而不是 Harness 本身。
- **Agent**：是最终跑起来的完整系统（Model + Harness）。

### 为什么现在这么重要？
2026 年行业共识已经从“模型够不够强”转向“**Harness 工程**”：

- 同样模型，换一套更好的 Harness，任务成功率可以大幅提升。
- 生产级 Agent 的瓶颈不再是推理能力，而是状态管理、工具可靠性、权限控制、长任务恢复、可观测性。
- Claude Code、Codex、Cursor、DeepSeek Harness、微软 Agent Framework 等产品，本质上都是高质量的 Harness 实现。

### 简单比喻
- 模型 = 发动机  
- Harness = 整车（底盘、方向盘、刹车、油门、仪表盘、安全气囊）  
- Agent = 能上路的汽车  

你不会只拿一个发动机去上班，同样也不会只拿一个裸模型去完成复杂工作。

**总结**：Harness 就是让大模型从“会说话”变成“会干活、且可控可靠”的那一层运行时系统。当前 Agent 工程的核心，已经从写提示词，进化到设计和打磨这层 Harness。
