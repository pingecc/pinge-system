所有编程语言都有自己的模块化，Java 里模块/包的概念非常清晰：`package` + `import` + 类文件组织 + 访问控制。JavaScript 的模块经历了从“无模块”到“多种方案并存”再到“ES Modules 成为标准”的漫长过程，目前主推ES6（ES2015），以文件为粒度的模块系统，现代浏览器和 Node.js 均原生支持，以前的方案这里就不讲了。

# 1. 核心设计理念

ES Modules 有几个关键设计原则：

| 特性                         | 说明                                                 | 对比 Java / CommonJS                                      |
| ---------------------------- | ---------------------------------------------------- | --------------------------------------------------------- |
| **静态结构**                 | `import` / `export` 必须写在顶层，不能放在 if/for 里 | Java 的 import 也是静态的；CommonJS 的 `require` 是动态的 |
| **编译时可知**               | 引擎在执行前就能完整构建模块依赖图                   | 利于 Tree Shaking、类型检查、打包优化                     |
| **Live Binding（实时绑定）** | 导入的是「绑定」而不是值的拷贝                       | 与 Java 静态导入后值拷贝不同                              |
| **默认严格模式**             | 模块内自动开启 `"use strict"`                        | 不用手动写                                                |
| **文件即模块**               | 一个 `.js` 文件就是一个模块                          | 比 Java 的「一个 public 类一个文件」更灵活                |
| **显式导出**                 | 只有被 `export` 的才对外可见                         | 类似 Java 的 public，未导出的都是私有                     |

# 2. 导出（export）详解

需要通过 `export` 关键字显示指定导出哪些。

## 2.1 命名导出（Named Export）——最推荐的方式

```js
// math.js

// 方式一：声明时直接导出
export const PI = 3.1415926;
export function add(a, b) {
  return a + b;
}
export class Calculator {
  multiply(a, b) {
    return a * b;
  }
}

// 方式二：先定义，再集中导出（推荐，可读性更好）
const subtract = (a, b) => a - b;
const multiply = (a, b) => a * b;

export { subtract, multiply };

// 方式三：导出时重命名
export { subtract as sub, multiply as mul };
```

特点：
- 一个模块可以有**多个**命名导出
- 导入时必须使用**相同的名字**（或用 `as` 重命名）
- 最有利于 Tree Shaking（打包工具可以精确删除未使用的导出）

## 2.2 默认导出（Default Export）

```js
// logger.js
export default function log(message) {
  console.log(`[LOG] ${message}`);
}

// 或者导出类
export default class Logger {
  constructor(name) {
    this.name = name;
  }
}

// 或者导出对象、基本类型等
export default {
  host: 'localhost',
  port: 3000
};
```

注意：
- **一个模块只能有一个默认导出**
- 默认导出在导入时可以随便起名字
- 实际项目中，命名导出通常更优（更明确、更好重构）





关于默认导出：

一个模块经常会有一个「最主要」的东西，例如：

- 一个类（`UserService`、`Router`、`Button`）
- 一个函数（`createApp`、`fetchUser`、`debounce`）
- 一个配置对象或实例

如果只用命名导出，导入时必须写花括号，并且名字必须对应：

```js
import { createApp } from './app.js';
import { UserService } from './UserService.js';
```

而默认导出允许你这样写：

```js
import createApp from './app.js';
import UserService from './UserService.js';
import MyUserService from './UserService.js';  // 名字可以随便取
```

**核心价值**：



**导出：**

```js
// 方式一：直接导出
export default function createApp() { ... }

// 方式二：先定义再导出
class UserService { ... }
export default UserService;

// 方式三：导出对象、值等
export default {
  host: 'localhost',
  port: 3000
};
```

**导入：**

```js
import createApp from './app.js';           // 最常见
import AnyNameYouLike from './app.js';     // 名字随意
import createApp, { version } from './app.js';  // 默认 + 命名混合
```

一个模块**最多只能有一个**默认导出。





虽然默认导出语法上很方便，但目前社区（包括很多大型项目和风格指南）越来越倾向于：

> **优先使用命名导出，谨慎使用默认导出。**

原因：

1. 命名导出对「自动重构」「全局搜索替换」「IDE 提示」更友好。
2. 默认导出容易造成同一个东西在不同文件里有不同的名字，增加阅读成本。
3. 一个模块如果真的只有一个主要导出，用命名导出也完全可以，而且更一致。

**折中建议**：

- 写 React/Vue 组件、工具函数库时，很多团队仍习惯默认导出组件本身。
- 写业务逻辑、工具方法、多功能模块时，优先全部用命名导出。
- 团队内部统一风格最重要。

# 3. 导入（import）详解

```js
// 1. 命名导入（名字必须对应）
import { PI, add, subtract as sub } from './math.js';

// 2. 默认导入（名字随便取）
import log from './logger.js';
import myLogger from './logger.js';

// 3. 默认 + 命名混合
import log, { PI, add } from './utils.js';

// 4. 命名空间导入（把所有命名导出装进一个对象）
import * as math from './math.js';
console.log(math.PI);
console.log(math.add(1, 2));

// 5. 只执行模块的副作用（不导入任何值）
import './init.js';
import './polyfill.js';

// 6. 动态导入（后面详细讲）
const math = await import('./math.js');
```

**重要规则**：
- `import` 语句会**提升**（hoisting），无论写在哪里，都会在模块执行前完成
- 路径在浏览器和带 `"type": "module"` 的 Node 中，通常建议写完整扩展名（`.js`）
- 相对路径以 `./` 或 `../` 开头；绝对路径或包名按解析规则处理



## 3.1 副作用导入

只导入模块并执行它，但不接收它的任何导出。

```js
import './init.js';
import './polyfill.js';
```

这在 ES Modules 里叫做 **副作用导入**（Side-effect Import）或 **空导入**。

1. **会执行模块里的顶层代码**  
   `init.js` 和 `polyfill.js` 文件会被加载、解析并执行。里面的所有顶层语句都会运行。

2. **不导入任何变量/函数**  
   即使这两个文件里有 `export`，当前模块也拿不到那些导出。  
   相当于告诉引擎：“我只需要这个模块跑一遍，不需要它的接口。”

3. **模块仍然会被缓存**  
   和其他正常导入一样，这两个模块只会执行一次。如果其他地方也导入了它们，不会重复执行。

常见使用场景

| 场景                 | 示例                              | 说明                                                      |
| -------------------- | --------------------------------- | --------------------------------------------------------- |
| **初始化逻辑**       | `import './init.js'`              | 做全局配置、注册事件、初始化环境等                        |
| **Polyfill（垫片）** | `import './polyfill.js'`          | 给旧浏览器补充新 API（如 `Promise`、`Array.includes` 等） |
| **全局样式**         | `import './global.css'`           | 在带打包工具的项目里引入 CSS（本身没有导出）              |
| **注册类/插件**      | `import './register-service.js'`  | 让模块在加载时自动注册到某个全局系统                      |
| **执行一次性代码**   | `import './setup-environment.js'` | 只需要副作用，不需要返回值                                |



**init.js**
```js
// 这个文件没有 export，只做副作用
console.log('系统初始化中...');
window.APP_CONFIG = { debug: true };
document.title = 'My App';
```

**polyfill.js**
```js
// 补充旧环境缺失的能力
if (!Array.prototype.includes) {
  Array.prototype.includes = function(value) {
    return this.indexOf(value) !== -1;
  };
}
```

**main.js**
```js
import './init.js';       // 执行初始化，不拿任何导出
import './polyfill.js';  // 打补丁，不拿任何导出

// 后面的代码就可以安全使用 polyfill 提供的能力了
console.log([1, 2, 3].includes(2)); // true
console.log(window.APP_CONFIG);     // { debug: true }
```

### 和普通导入的区别

```js
// 普通导入：执行模块 + 拿到导出
import { something } from './module.js';
import mod from './module.js';
import * as mod from './module.js';

// 副作用导入：只执行模块，不拿导出
import './module.js';
```

### 关于顶层语句

**顶层语句（Top-level statements）**指的是：写在模块文件**最外层**、没有被包裹在函数、类、块级作用域里的那些代码。

当一个模块被导入时（包括 `import './init.js'` 这种副作用导入），引擎会执行该模块里**所有的顶层代码**。

1. 什么是顶层语句？

简单判断标准：

> 这段代码在模块加载时就会立刻执行，而不是等你调用某个函数或实例化某个类才执行。

属于顶层、会被执行的代码示例：

```js
// init.js

console.log('这行会执行');                    // ✅ 顶层

const name = '张三';                           // ✅ 顶层变量声明
let count = 0;                                // ✅

function helper() {                           // ✅ 函数声明本身会执行（定义函数）
  console.log('但函数体不会自动执行');
}

class User {                                  // ✅ 类声明本身会执行（定义类）
  constructor() {
    console.log('构造函数不会自动执行');
  }
}

const user = new User();                      // ✅ 这行会执行，所以会打印构造函数里的内容

if (true) {                                   // ✅ if 是顶层的，会执行
  console.log('条件成立，这行也会执行');
}

for (let i = 0; i < 3; i++) {                 // ✅ 循环会执行
  console.log(i);
}

// 立即执行函数（IIFE）
(function () {
  console.log('IIFE 会执行');
})();

// 赋值、函数调用等
window.APP_READY = true;                      // ✅
initApp();                                    // ✅ 调用函数会执行
doSomething();                                // ✅
```

以上所有代码在模块被导入时**都会运行**。

---



2. 不属于顶层、不会自动执行的代码

```js
// init.js

function helper() {
  console.log('这行不会自动执行');            // ❌ 在函数体内
  const x = 10;                               // ❌
}

class User {
  constructor() {
    console.log('不会自动执行');              // ❌ 在构造函数里
  }

  sayHello() {
    console.log('也不会自动执行');            // ❌ 在方法里
  }
}

const obj = {
  method() {
    console.log('不会自动执行');              // ❌ 在对象方法里
  }
};

// 只有被调用时才会执行
helper();         // 如果这行在顶层，才会执行 helper 里面的代码
new User();       // 如果这行在顶层，才会执行构造函数
```

---





- **顶层语句** = 写在模块文件最外层的代码（变量声明、函数/类声明、表达式、if/for、函数调用等）。
- 模块被导入时，这些顶层语句会**立即按顺序执行一次**。
- 函数体、类方法体、对象方法里的代码**不会**自动执行，只有被调用时才会运行。

这就是为什么 `import './init.js'` 或 `import './polyfill.js'` 能起到“执行初始化 / 打补丁”的作用。



## 路径查找机制

**JavaScript 模块路径查找机制 & 包（Package）的概念**

JavaScript 的模块路径解析（Module Resolution）和 Java 的包机制有相似之处，但更灵活，也更依赖运行环境（浏览器 vs Node.js）。

---

### 1. 整体概览

导入语句里的路径主要分为三类：

| 类型                           | 示例                                              | 说明                                     |
| ------------------------------ | ------------------------------------------------- | ---------------------------------------- |
| **相对路径**                   | `'./utils.js'`、`'../common/math.js'`             | 最常用，相对于当前模块的位置             |
| **绝对路径 / URL**             | `'/src/utils.js'`、`'https://example.com/lib.js'` | 浏览器中常见；Node 中较少用              |
| **裸说明符（Bare Specifier）** | `'lodash'`、`'react'`、`'@vue/shared'`            | 类似“包名”，需要解析机制才能找到实际文件 |

---

### 2. 浏览器中的解析规则

浏览器对 ES Modules 的支持比较“原生”和严格：

```js
import { add } from './math.js';          // ✅ 相对路径
import { add } from '../utils/math.js';   // ✅
import _ from 'https://cdn.skypack.dev/lodash';  // ✅ URL
import { something } from 'lodash';       // ❌ 默认不支持（裸说明符）
```

- 相对路径和绝对路径按 URL 规则解析。
- **默认不支持**直接写包名（`'lodash'`）。
- 想用包名，通常有两种方式：
  1. 使用 **Import Maps**（浏览器原生支持）：
     ```html
     <script type="importmap">
     {
       "imports": {
         "lodash": "/node_modules/lodash-es/lodash.js",
         "react": "https://esm.sh/react"
       }
     }
     </script>
     ```
  2. 使用打包工具（Vite、Webpack、esbuild 等）在构建阶段把裸说明符解析掉。

浏览器本身**没有**像 Node 那样完整的 `node_modules` 查找机制。

---

### 3. Node.js 中的模块解析（重点）

Node.js 有一套完整的解析算法，也是前端工程化中最常接触的部分。

#### 3.1 相对路径 / 绝对路径

```js
import { add } from './math.js';
import { add } from '../utils/math.js';
import { add } from '/absolute/path/math.js';
```

查找规则相对直观：
1. 按路径去找文件。
2. 如果没写扩展名，Node 会尝试补全（在 ESM 中行为比 CommonJS 更严格，通常建议写全 `.js`）。
3. 如果路径指向目录，会尝试找该目录下的 `package.json` 的 `main`/`exports`，或 `index.js`。

#### 3.2 裸说明符（包名）的解析 —— 真正的“包”查找

```js
import _ from 'lodash';
import { debounce } from 'lodash-es';
import React from 'react';
```

查找过程（简化版）：

1. 从**当前文件所在目录**开始，向上逐级查找 `node_modules` 文件夹。
2. 在某个 `node_modules` 里找到对应名称的包（例如 `node_modules/lodash`）。
3. 读取该包的 `package.json`。
4. 根据 `package.json` 的字段决定实际加载哪个文件：
   - 优先使用 **`exports`** 字段（现代标准）
   - 其次是 `module`（历史字段，指向 ESM 版本）
   - 再次是 `main`（CommonJS 入口）
   - 都没有则尝试 `index.js`

这就是 JavaScript 生态中的 **包（Package）** 概念。

---

### 4. JavaScript 中的“包”到底是什么？

和 Java 的 package + Maven/Gradle 坐标类似，但更轻量：

| 概念         | Java                         | JavaScript (Node)                           |
| ------------ | ---------------------------- | ------------------------------------------- |
| 包的基本单位 | 一个 package + 多个 class    | 一个文件夹 + 一个 `package.json`            |
| 包的身份标识 | `groupId:artifactId:version` | `name` + `version`（在 `package.json`）     |
| 依赖存放位置 | 本地仓库 / `.m2`             | 项目下的 `node_modules`                     |
| 依赖声明     | `pom.xml` / `build.gradle`   | `package.json` 的 `dependencies`            |
| 入口文件     | 类的全限定名                 | `package.json` 的 `main` / `exports` 等字段 |

一个最简单的包结构：

```
my-utils/
├── package.json          ← 包的“身份证”
├── index.js              ← 入口
├── math.js
└── string.js
```

`package.json` 示例：

```json
{
  "name": "my-utils",
  "version": "1.0.0",
  "type": "module",
  "main": "./index.js",
  "exports": {
    ".": "./index.js",
    "./math": "./math.js",
    "./string": "./string.js"
  }
}
```

---

### 5. 现代包导出控制：`exports` 字段（非常重要）

这是目前控制包公共 API 的最推荐方式。

```json
{
  "name": "my-lib",
  "exports": {
    ".": {
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.js"
    },
    "./utils": "./dist/esm/utils.js",
    "./package.json": "./package.json"
  }
}
```

作用：
- 精确控制外部能导入包的哪些路径（封装内部实现）。
- 支持**条件导出**（根据 `import` / `require`、浏览器/Node、开发/生产等返回不同文件）。
- 防止用户深入导入包内部的私有文件。

---

### 6. 其他相关机制

- **`imports` 字段**（package.json）：用于包**内部**的路径别名，类似内部的 import map。
- **TypeScript 路径别名**（`tsconfig.json` 的 `paths`）：只在编译期生效，最终还是要靠打包工具或 Node 解析。
- **打包工具的解析**：Vite、Webpack 等会在 Node 解析规则基础上，再叠加自己的 alias、extensions 等配置。

---

### 7. 总结

| 问题                 | 答案                                                         |
| -------------------- | ------------------------------------------------------------ |
| 导入时如何查找模块？ | 相对/绝对路径按文件位置找；裸说明符（包名）在 Node 中通过 `node_modules` + `package.json` 查找 |
| 有没有“包”的概念？   | **有**，而且非常核心。一个包 ≈ 带 `package.json` 的文件夹，通过 npm 生态管理和分发 |
| 浏览器和 Node 的差异 | 浏览器原生不支持裸说明符，需要 Import Maps 或打包工具；Node 内置了完整的包解析算法 |
| 和 Java 包的对比     | 更灵活、以文件和 `package.json` 为中心，没有强制的目录与包名对应关系 |







# 4. ES Modules 的工作机制

ES Modules 的加载分为三个主要阶段（比 CommonJS 复杂但更强大）：

1. **构建（Construction）**  
   - 下载/读取模块文件  
   - 解析成 Module Record  
   - 递归构建整个依赖图（Module Graph）  
   - 此阶段**只解析，不执行代码**

2. **实例化（Instantiation）**  
   - 为每个导出创建「绑定」（binding）  
   - 连接导入和导出的绑定关系（Live Binding 的基础）  
   - 还没执行代码

3. **评估（Evaluation）**  
   - 从入口模块开始，深度优先执行模块代码  
   - 每个模块只执行一次（有缓存）

**Live Binding 示例**（非常重要）：

```js
// counter.js
export let count = 0;

export function increment() {
  count++;
}

// main.js
import { count, increment } from './counter.js';

console.log(count);   // 0
increment();
console.log(count);   // 1  ← 直接看到最新值，不是拷贝
```

这与 CommonJS（拷贝值）和 Java 的静态导入有本质区别。

---

### 5. 高级特性

#### 5.1 动态导入 `import()`

```js
// 返回 Promise，可以按需、条件加载
const button = document.getElementById('load');
button.addEventListener('click', async () => {
  const module = await import('./heavy-module.js');
  module.doSomething();
});

// 结合条件
if (condition) {
  const { utils } = await import('./utils.js');
}
```

用途：路由懒加载、大型库按需加载、代码分割。

#### 5.2 `import.meta`

```js
console.log(import.meta.url);     // 当前模块的完整 URL
console.log(import.meta.filename); // Node.js 中的文件路径（较新）
console.log(import.meta.dirname);  // Node.js 中的目录路径（较新）
```

浏览器和 Node 的 `import.meta` 内容略有不同。

#### 5.3 顶层 await（Top-level await）

只有在 ES Modules 中才允许：

```js
// data.js
const response = await fetch('https://api.example.com/data');
const data = await response.json();

export { data };
```

模块会等待顶层 await 完成后再继续执行依赖它的模块。

#### 5.4 导入属性（Import Attributes，原 Import Assertions）

```js
import data from './config.json' with { type: 'json' };
import styles from './style.css' with { type: 'css' };
```

用于明确告诉引擎如何解析非 JS 模块。

# 6. 在不同环境中的使用

## 浏览器

```html
<!-- 普通脚本 -->
<script src="js/login.js"></script>

<!-- ES 模块. 以 ES Module 的方式加载并执行 js/login.js 文件。 -->



<script type="module">
  import { add } from './math.js';
  console.log(add(1, 2));
</script>
```

这行代码的意思是：**以 ES Module 的方式加载并执行 `js/login.js` 文件**。
```html
<script type="module" src="js/login.js"></script>
```

| 部分 | 含义 |
|------|------|
| `<script>` | 引入外部 JavaScript 文件 |
| `type="module"` | **关键**：告诉浏览器「这是一个 ES 模块」，而不是普通脚本 |
| `src="js/login.js"` | 文件路径 |

### `type="module"` 作用

和普通的 `<script src="...">` 相比，主要有这些区别：

 1. 自动开启严格模式
模块代码默认运行在严格模式（`'use strict'`）下，不需要自己写。

 2. 支持 `import` / `export`
可以在文件里使用模块语法：

```js
// login.js
import { Auth } from './auth.js';   // 引入其他模块

export function doLogin() {        // 导出自己的功能
  // ...
}
```

普通 `<script>` 是不支持 `import/export` 的。

 3. 默认延迟执行（相当于加了 `defer`）
- 普通脚本：下载完就立刻执行，可能会阻塞 HTML 解析
- 模块脚本：**等 HTML 解析完成后再执行**，并且会按顺序执行

 4. 作用域是模块作用域
模块顶层声明的变量（`let`/`const`/`var`/`function`）**不会变成全局变量**，外面访问不到，避免污染全局。

 5. 只会执行一次
同一个模块被多次 `import` 或多次用 `<script type="module">` 引入，也只执行一次（有缓存）。

 6. 必须通过服务器访问（或特殊配置）
直接用 `file://` 协议打开 HTML，模块通常会报跨域错误。需要用本地服务器（比如 Live Server、vite、http-server 等）才能正常运行。

### 示例

假设你有两个文件：

**js/auth.js**
```js
export const Auth = {
  login() { /* ... */ },
  logout() { /* ... */ }

```

**js/login.js**
```js
import { Auth } from './auth.js';

document.querySelector('#login-btn').addEventListener('click', () => {
  Auth.login();
});
```

**HTML**
```html
<script type="module" src="js/login.js"></script>
```

浏览器会自动处理模块依赖，先加载 `auth.js`，再执行 `login.js`。








```html
<script type="module" src="main.js"></script>


```

特点：
- 自动延迟执行（类似 `defer`）
- 支持跨域（需要 CORS）
- 本地文件直接用 `file://` 协议会有限制，建议用本地服务器

## Node.js

有三种主要方式启用 ESM：

1. **推荐**：`package.json` 中设置
   ```json
   {
     "type": "module"
   }
   ```
   之后 `.js` 文件都按 ESM 处理。

2. 文件扩展名使用 `.mjs`

3. CommonJS 文件用 `.cjs` 强制保持 CJS

**Node 的模块解析**还支持 `package.json` 的 `exports` 字段（条件导出），非常强大，可以实现：
- 不同环境导出不同文件
- 隐藏内部文件
- 同时支持 `import` 和 `require`

### 7. 与 CommonJS 的互操作

| 方向         | 支持情况       | 说明                                                       |
| ------------ | -------------- | ---------------------------------------------------------- |
| ESM 导入 CJS | 支持           | `import pkg from 'cjs-package'`，得到的是 `module.exports` |
| CJS 导入 ESM | **不支持同步** | 必须使用动态 `import()`                                    |
| 混合使用     | 谨慎           | 容易出现“双模块实例”问题                                   |

---

### 8. 常见坑与最佳实践

**常见坑**：
1. 忘记写文件扩展名（浏览器和部分 Node 配置下会报错）
2. 把 `import` 写在条件语句或函数里（语法错误）
3. 默认导出和命名导出混淆
4. 循环依赖虽然语法支持，但设计上应尽量避免
5. 在 CommonJS 项目中直接使用 ESM 语法导致报错

**推荐实践**：
- 新项目一律使用 ES Modules
- **优先使用命名导出**，默认导出仅在“模块核心就是一个东西”时使用
- 使用 `index.js` 做统一导出（barrel file），但注意不要过度
- 路径尽量写清楚，团队统一是否带扩展名
- 使用 TypeScript 时，模块相关配置（`module`、`moduleResolution`）要匹配
- 工具链优先选择对 ESM 友好的：Vite、esbuild、Rollup、Webpack 5+

### 9. 与 Java 的快速对照

| Java                             | ES Modules                         |
| -------------------------------- | ---------------------------------- |
| `package com.example;`           | 文件路径本身就是模块标识           |
| `import com.example.MathUtils;`  | `import { add } from './math.js';` |
| `public class` / `public static` | `export`                           |
| 未 public 的成员                 | 不写 `export` 的变量/函数          |
| 静态导入后值拷贝                 | Live Binding（实时绑定）           |
| 编译期检查                       | 静态分析 + 引擎检查                |
| Maven/Gradle 依赖                | npm + package.json                 |
