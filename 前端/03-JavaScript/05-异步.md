**JavaScript 异步编程：从单线程到 async/await**


# 第 1 层：为什么需要异步 —— JavaScript 是单线程的

## 1.1 单线程意味着什么

JavaScript 的**主执行线程只有一个**（Call Stack 只有一个）。

- 同一时刻只能执行一段同步代码。
- 没有像 Java 那样的多线程并发执行业务逻辑（虽然有 Web Worker / Node Worker Threads，但它们与主线程隔离，不能直接操作 DOM 或共享内存，使用场景有限）。

## 1.2 为什么设计成单线程

- **浏览器环境**：操作 DOM 必须保证安全，多线程同时改 DOM 会出大问题（需要加锁，复杂度极高）。
- **历史原因 + 简单性**：语言最初就是为浏览器脚本设计的。

## 1.3 代价：同步代码会卡住页面

如果一段代码执行时间很长（比如复杂计算），会**阻塞**整个页面（卡顿、无响应）。所以 JS 强调「不要做长时间同步计算」，重活要么拆分，要么丢给 Worker。

**于是异步成为必然选择**：耗时操作（定时、网络、文件 I/O 等）交给宿主环境（浏览器 / Node.js）的底层能力去办，主线程先继续做自己的事，等结果好了再回来处理。下面的每一层分别回答这个机制的一个侧面。

# 第 2 层：异步如何实现 —— 事件循环（Event Loop）

一切异步的实现，都围绕四个角色：

## 2.1 四个核心角色

1. **Call Stack（调用栈）**
   主线程正在执行的代码都在这里。同一时间只能有一个东西在跑。

2. **Web APIs / Node 底层能力（真正干活的人）**
   浏览器或 Node.js 提供的**其他线程** / 系统能力，比如：
   - 定时器线程
   - 网络请求线程
   - 文件 I/O 线程
   - 等等

3. **任务队列（Task Queue）**
   用来存放「已经完成的异步操作的回调函数」。严格来说它的全名是**宏任务队列**（Macrotask Queue），下一层细讲。

4. **事件循环（Event Loop）**
   不断盯着调用栈，一旦调用栈空了，就从任务队列里拿一个回调出来，放进调用栈执行。

它们的关系可以这样理解：

```
  同步代码 ──执行──▶ Call Stack（调用栈）
                          │ 空了？
                          ▼
                    Event Loop ◀──取出回调── Task Queue（任务队列）
                          ▲                        │
                          │ 注册                   │ 完成后回调入队
                          ▼                        ▼
                 Web APIs / Node 底层能力（定时器、网络、I/O…）
```

## 2.2 案例拆解：定时器 setTimeout

```js
console.log('开始');

setTimeout(() => {
  console.log('定时器到了');
}, 2000);

console.log('结束');
```

我们按**真实发生的时间顺序**来看。

**第 0 毫秒（主线程开始执行）**

1. 遇到 `console.log('开始')` → 直接在调用栈执行，打印「开始」。
2. 遇到 `setTimeout(..., 2000)` —— **这里是关键点**：
   JavaScript **并没有自己去计时**，而是对浏览器说：

   > 「帮我计时 2 秒，时间到了以后，把这个箭头函数放到任务队列里。」

   然后**主线程立刻继续往下执行**，不会在这里等。
3. 遇到 `console.log('结束')` → 打印「结束」。

此时调用栈已经空了。

**第 0 ~ 2000 毫秒之间**

- 主线程空闲（或者在做别的事）。
- **浏览器的定时器线程**在后台默默计时（这是真正的其他线程在工作）。

**第 2000 毫秒时**

- 定时器线程发现时间到了，把回调函数 `() => { console.log('定时器到了') }` **放进任务队列**（即宏任务队列，下一层细讲）。

**事件循环开始工作**

事件循环一直在检查：「调用栈空了吗？空了的话，任务队列里有没有东西？」发现有，就取出这个回调，推入调用栈执行 → 打印「定时器到了」。

**核心结论**

- 主线程从来没有真正「等待」过那 2 秒。
- 真正计时的是浏览器提供的**其他线程**。
- 主线程只是注册了一下任务，然后继续干自己的事。
- 等别人干完了，通过「任务队列」通知主线程来执行回调。

这就是**「异步非阻塞」**的本质。

## 2.3 案例拆解：网络请求 fetch

```js
console.log('1');

fetch('https://api.example.com/data')
  .then(res => res.json())
  .then(data => console.log('数据到了', data));

console.log('2');
```

时间线：

1. 打印 `1`
2. 遇到 `fetch`：
   - JS 引擎告诉浏览器网络模块：「帮我发这个 HTTP 请求」
   - 主线程**立刻继续**，打印 `2`
3. 浏览器的网络线程去发请求、等服务器响应（可能要几百毫秒）
4. 响应回来后，网络模块把「成功回调」放入任务队列
5. 事件循环发现调用栈空了，就把回调拿出来执行（进入 `.then`）

所以你看到的效果是：`1` 和 `2` 几乎瞬间打印，数据过一会儿才到。

# 第 3 层：事件循环的调度规则 —— 宏任务与微任务

第 2 层了解了事件循环的大框架，但任务队列里的任务并不是「先来先走」这么简单：异步回调之间还有**优先级**之分，这就是宏任务与微任务。

JavaScript 是单线程的，所有异步操作最终都要通过事件循环（Event Loop）调度执行。微任务和宏任务**都是由事件循环调度的**，浏览器和 Node.js 都遵循类似的规则。

## 3.1 调度规则：一个宏任务 → 清空微任务 → 下一个宏任务

正确的执行流程是：

1. **先执行当前的一个宏任务**（最开始的同步代码也可以看作第一个宏任务）。
2. **执行完这一个宏任务后，立刻检查微任务队列**。
3. **如果微任务队列里有任务，就把它们全部执行完**（哪怕执行过程中又产生了新的微任务，也会继续清空，直到队列为空）。
4. 微任务清空后，如果有需要，浏览器可能会进行一次渲染。
5. 然后再从宏任务队列里取出**下一个**宏任务，重复以上过程。

## 3.2 宏任务（Macrotask）

宏任务是事件循环的**基本单元**，每个循环周期只执行**一个**宏任务。

**常见的宏任务来源：**

- `setTimeout` / `setInterval`
- `setImmediate`（Node.js）
- `I/O` 操作（文件读写、网络请求）
- `UI rendering`（浏览器重绘）
- `MessageChannel`
- `requestAnimationFrame`

**特点：** 执行完一个宏任务后，浏览器可能会进行渲染（如果有需要），然后进入下一个事件循环周期。

## 3.3 微任务（Microtask）

微任务是在**当前宏任务执行完毕后、下一个宏任务开始之前**立即执行的任务。一个事件循环周期内可以执行**多个**微任务，直到微任务队列清空。

**常见的微任务来源：**

- `Promise.then()` / `Promise.catch()` / `Promise.finally()`
- `MutationObserver`
- `queueMicrotask()`
- `process.nextTick`（Node.js，优先级比微任务还高）

**特点：**

- **优先级高于宏任务** —— 宏任务执行完后，会先清空所有微任务，再去执行下一个宏任务。
- **会阻塞渲染** —— 微任务队列没清空前，浏览器不会进行 UI 渲染。

## 3.4 微任务不是 Promise 发明的

在 Promise 标准化（ES6，2015 年）之前，**微任务机制已经存在**，只是没有现在这么"显眼"：

- **`MutationObserver`**（2012 年左右引入）就是典型的微任务。它用于监听 DOM 变化，其回调会被放入微任务队列，在当前脚本执行完毕后立即执行。
- **Node.js 的 `process.nextTick`** 甚至比 Promise 更早，虽然严格来说它优先级比微任务还高，但概念上属于"在当前操作完成后立即执行"的机制。

所以，**微任务队列不是 Promise 发明的**，而是浏览器 / JS 引擎内部早已有的一种调度机制。

Promise 的贡献在于：

1. **让微任务机制"显性化"和"标准化"**
   在 Promise 之前，普通开发者很少需要关心"微任务"这个概念。`setTimeout` 是大家处理异步的主要方式，而 `MutationObserver` 使用场景相对小众。Promise 的 `.then()` 让**每个前端开发者都不得不面对微任务**，从而把微任务从"引擎内部机制"变成了"开发者必须理解的概念"。

2. **提供了比宏任务更精细的调度粒度**
   在 Promise 出现前，如果你想"尽快"执行一个异步回调，只能用 `setTimeout(fn, 0)`，但它最少也有 4ms 延迟（HTML5 规范限制），而且要等到下一个宏任务周期。Promise 让回调可以在**当前执行栈清空后立即执行**，无需等待下一个宏任务周期。

## 3.5 理解"当前执行栈"：微任务不会插队

规则一句话：

> **执行栈（Call Stack）就是当前正在运行的代码的"调用链条"。只有当这个链条上的所有函数都执行完毕、栈被清空后，事件循环才会去处理微任务队列。**

执行栈是一个**后进先出（LIFO）**的数据结构。每当调用一个函数，它就被压入栈顶；函数执行完毕，就从栈顶弹出。

### 3.5.1 最小例子：A / C / B

```javascript
console.log('A');
Promise.resolve().then(() => console.log('B'));
console.log('C');
```

整个 `<script>` 标签（或这个模块）的代码本身就是一个**宏任务**。它的执行过程如下：

```
1. 全局执行上下文入栈
        ↓
2. console.log('A') 入栈 → 执行 → 出栈
        ↓
3. Promise.resolve() 入栈 → 执行 → 出栈
   （注意：.then() 只是把回调注册到微任务队列，不会入栈执行）
        ↓
4. console.log('C') 入栈 → 执行 → 出栈
        ↓
5. 全局执行上下文出栈 ← 执行栈清空！
        ↓
6. 检查微任务队列 → 发现 B → 执行 console.log('B')
```

**输出：**

```
A
C
B
```

### 3.5.2 栈里还有代码，微任务不插队

如果在打印 C 之后还有同步代码，会继续执行么？还是先执行打印 B 的微任务？

**会继续执行同步代码，微任务不会插队。**

```javascript
console.log('A');

Promise.resolve().then(() => console.log('微任务 B'));

console.log('C');

console.log('D');  // ← C 后面还有同步代码

function foo() {
    console.log('E');
}
foo();  // ← 还有函数调用

console.log('F');  // ← 还有同步代码
```

**执行顺序是：**

```
A
C
D
E
F
微任务 B
```

**原因：** 从 `A` 到 `F`，所有同步代码都属于**同一个执行栈**。只要栈里还有代码在跑，微任务就只能乖乖在队列里等着。**只有整个执行栈彻底清空后**，引擎才会转头去看微任务队列。

### 3.5.3 嵌套函数也一样

```javascript
function outer() {
    console.log('1');

    Promise.resolve().then(() => console.log('微任务'));

    inner();
    console.log('3');
}

function inner() {
    console.log('2');
}

outer();
console.log('4');
```

执行过程：

```
outer() 入栈
  console.log('1') 入栈 → 执行 → 出栈    // 输出 1
  Promise.then() 注册微任务（只注册，不执行）
  inner() 入栈
    console.log('2') 入栈 → 执行 → 出栈  // 输出 2
  inner() 出栈
  console.log('3') 入栈 → 执行 → 出栈    // 输出 3
outer() 出栈
console.log('4') 入栈 → 执行 → 出栈      // 输出 4

← 执行栈清空！
检查微任务队列 → 执行微任务              // 输出 微任务
```

**输出：**

```
1
2
3
4
微任务
```

## 3.6 一个 `<script>` 标签就是一个宏任务

**一个 `<script>` 标签（或一个模块）本身就是一个宏任务。**

所以正确的说法是：

> **当前这一个宏任务（比如当前 `<script>` 标签里的同步代码）执行完毕后**，才会去检查微任务队列。而不是等页面里**所有** `<script>` 标签都跑完。

### 多脚本的真实场景

假设 HTML 里有多个脚本：

```html
<script>
    console.log('脚本1 - A');
    Promise.resolve().then(() => console.log('脚本1 - 微任务'));
    console.log('脚本1 - B');
</script>

<script>
    console.log('脚本2 - C');
</script>
```

**执行顺序是：**

```
脚本1 - A
脚本1 - B
脚本1 - 微任务   ← 第一个 script（宏任务）结束后立刻执行
脚本2 - C        ← 然后才进入第二个 script（下一个宏任务）
```

**不是：**

```
脚本1 - A
脚本1 - B
脚本2 - C        ← 错误！不会等所有脚本跑完
脚本1 - 微任务
```

### 动态插入脚本

```javascript
console.log('1');

// 动态创建另一个脚本（这会触发一个新的宏任务）
const script = document.createElement('script');
script.textContent = `
    console.log('3');
    Promise.resolve().then(() => console.log('脚本2的微任务'));
`;
document.head.appendChild(script); // 插入后立即执行

Promise.resolve().then(() => console.log('脚本1的微任务'));

console.log('2');
```

**输出：**

```
1
2
脚本1的微任务    ← 当前宏任务（第一个脚本）结束，先清它的微任务
3
脚本2的微任务    ← 然后执行新插入的脚本（新宏任务），再清它的微任务
```

**正确口诀：**

> **一个宏任务内的同步代码 → 该宏任务产生的微任务 → 下一个宏任务**

每个 `<script>`、每个 `setTimeout` 回调、每个用户点击回调，都是独立的宏任务。宏任务与宏任务之间，才会插入微任务的清理。

## 3.7 综合题目：经典对比示例

```javascript
console.log('script start');

setTimeout(() => {
    console.log('setTimeout');
}, 0);

Promise.resolve().then(() => {
    console.log('promise1');
}).then(() => {
    console.log('promise2');
});

console.log('script end');
```

**执行顺序解析：**

1. `script start` —— 同步代码
2. `script end` —— 同步代码
3. `promise1` —— 同步代码执行完，先清空微任务队列
4. `promise2` —— 继续清空微任务队列（then 链式调用会产生新的微任务）
5. `setTimeout` —— 微任务队列清空，执行下一个宏任务

**输出：**

```
script start
script end
promise1
promise2
setTimeout
```

**本层小结：**

- **宏任务**是事件循环的"大节拍"，每个循环处理一个，中间可能穿插渲染。
- **微任务**是"插队"执行的，在当前宏任务结束后立即全部清空，优先级高于宏任务和渲染。
- **Promise 的构造函数同步执行**，但 `.then()` 的回调会被包装成**微任务**，在当前执行栈清空后优先执行。

## 3.8 补充：浏览器与 Node.js 的差异

浏览器和 Node.js 遵循同一套「宏任务 → 清空微任务 → 下一个宏任务」的规则，但 Node.js 有两处细节不同：

- **`process.nextTick` 优先级比 Promise 微任务还高**：它有一个独立的队列，在当前阶段结束、Promise 微任务之前执行。
- **`setImmediate` 与 `setTimeout(fn, 0)` 的先后取决于阶段**：在 I/O 回调内部执行时，`setImmediate` 一定先到；在主模块顶层则顺序不确定。

```js
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('microtask'));
setTimeout(() => console.log('setTimeout'), 0);
```

**输出：** `nextTick` → `microtask` → `setTimeout`。

# 第 4 层：Promise —— 异步编程的容器

前面几层解决了「异步怎么跑起来、何时执行」的问题，这一层解决「异步的结果怎么表达与组合」的问题。

## 4.1 为什么需要 Promise：回调地狱

早期 JS 异步全靠**回调函数**：

```js
fs.readFile('a.txt', (err, data) => {
  if (err) { /* 处理错误 */ }
  fs.readFile('b.txt', (err2, data2) => {
    // 继续嵌套……
  });
});
```

问题非常明显：

- **回调地狱**（Callback Hell）：层层嵌套，可读性极差。
- 错误处理分散，容易漏掉。
- 无法方便地组合、取消、超时控制。

Promise 就是为了解决这些问题而生的。

## 4.2 Promise 是什么：状态机

Promise 是一个代表未来某个异步操作结果的**对象**。它有三种状态：

| 状态 | 含义 | 是否可变 |
| --- | --- | --- |
| `pending` | 进行中 | 可变为其他状态 |
| `fulfilled` | 成功（有值） | 终态 |
| `rejected` | 失败（有原因） | 终态 |

一旦变成 `fulfilled` 或 `rejected`，就不可再变。这和 Java 中的 `CompletableFuture` 的完成状态非常类似。

## 4.3 创建 Promise

```js
const p = new Promise((resolve, reject) => {
  // 异步操作
  setTimeout(() => {
    if (Math.random() > 0.5) {
      resolve('成功结果');   // 变成 fulfilled
    } else {
      reject(new Error('失败原因')); // 变成 rejected
    }
  }, 1000);
});
```

- `resolve(value)` → 成功，把 Promise 标记为**成功（fulfilled）**，并把 value 作为成功的结果。
- `reject(reason)` → 失败（通常传 Error 对象），把 Promise 标记为**失败（rejected）**，并把 reason 作为失败的原因。

> Promise 一旦被 resolve 或 reject（状态变为 settled），就**不可再改变**。

```js
// 调用 resolve 之后，后续 then() 回调的参数来自 resolve 传入的 value
const p1 = new Promise((resolve, reject) => {
  resolve('成功了');
});
p1.then(value => {
  console.log(value);   // 输出：成功了
});

// 调用 reject，后续 catch 的参数来自 reject 传入的 reason
const p2 = new Promise((resolve, reject) => {
  reject(new Error('出错了'));
});
p2.catch(err => {
  console.error(err.message);  // 输出：出错了
});
```

## 4.4 消费 Promise：then / catch / finally 与链式调用

```js
p.then(
  value => console.log('成功:', value),   // onFulfilled
  reason => console.error('失败:', reason) // onRejected（可选）
);
```

更常见的是链式写法 + 单独的 `.catch()`：

```js
p
  .then(value => {
    console.log(value);
    return value + ' 加工后';
  })
  .then(processed => console.log(processed))
  .catch(err => console.error(err))
  .finally(() => console.log('无论成功失败都会执行'));
```

**重要特性：**

- `.then()` 返回的是**新的 Promise**，所以可以链式调用。
- 如果在 `.then()` 里返回一个值，下一个 `.then()` 会收到这个值。
- 如果返回另一个 Promise，会等待它完成（自动展开）。
- 如果抛出异常或返回 `reject`，会进入 `.catch()`。

## 4.5 静态方法与组合

```js
// 快速创建已完成的 Promise
Promise.resolve(42);
Promise.reject(new Error('fail'));

// 并行等待全部成功（有一个失败就失败）——类似 CompletableFuture.allOf
Promise.all([p1, p2, p3])
  .then(([r1, r2, r3]) => { /* 全部成功 */ });

// 全部结束（无论成功失败），返回结果数组（含状态）
Promise.allSettled([p1, p2, p3]);

// 谁先完成就用谁（成功或失败都算）
Promise.race([p1, p2]);

// 谁先成功就用谁（忽略失败的）
Promise.any([p1, p2]);
```

这些和 Java 的 `CompletableFuture.allOf`、`anyOf` 思路非常接近，只是 API 更简洁。

## 4.6 Promise 的执行时机：构造函数同步，回调是微任务

这是所有相关面试题的核心，也是「Promise 的异步到底在哪里」的答案：

**Promise 本身不是异步的，它的构造函数是同步执行的。真正异步的是 `.then()` / `.catch()` / `.finally()` 里的回调函数，它们会被放入微任务队列。**

```javascript
console.log('1. 开始');

const p = new Promise((resolve, reject) => {
    console.log('2. Promise 构造函数（同步执行）');
    resolve('成功');
});

p.then(value => {
    console.log('4. then 回调（微任务）', value);
});

console.log('3. 结束');
```

**输出顺序：**

```
1. 开始
2. Promise 构造函数（同步执行）
3. 结束
4. then 回调（微任务） 成功
```

再看一个等价的最小例子：

```js
console.log('start');

Promise.resolve().then(() => {
  console.log('promise then');
});

console.log('end');
```

执行过程：

1. `console.log('start')` → 同步执行
2. `Promise.resolve().then(...)`
   - 创建一个已经成功的 Promise（同步）
   - 把 `.then` 里的回调**放入微任务队列**
3. `console.log('end')` → 同步执行
4. 同步代码全部执行完，调用栈空了
5. 事件循环先清空**微任务队列** → 打印 `promise then`

所以 Promise 的「异步」不是因为它自己开了线程，而是因为它把回调放进了**微任务队列**，等当前同步代码执行完再执行。

# 第 5 层：async / await —— 让异步代码像同步

`async/await` 是 Promise 的**语法糖**，让代码读起来像同步，但底层仍然是 Promise + 事件循环。

## 5.1 基本用法

```js
async function fetchData() {
  try {
    const res = await fetch('/api/user');   // 等待 Promise 完成
    const data = await res.json();
    return data;
  } catch (err) {
    console.error('出错了', err);
    throw err; // 可以继续抛出
  } finally {
    console.log('清理工作');
  }
}
```

## 5.2 关键点

- `async` 函数**永远返回 Promise**。即使你 `return 1`，实际返回的是 `Promise.resolve(1)`。
- `await` 只能用在 `async` 函数内部（或顶层模块）。
- `await` 会暂停当前 `async` 函数的执行，直到 Promise 完成，然后继续；暂停期间，事件循环仍然可以处理其他任务。
- 出错时，`await` 会抛出异常，用 `try/catch` 捕获（非常像同步代码）。

## 5.3 对比 Promise 链式写法

```js
// Promise 链式
function fetchData() {
  return fetch('/api/user')
    .then(res => res.json())
    .then(data => data)
    .catch(err => { /* ... */ });
}

// async/await 写法（更直观）
async function fetchData() {
  try {
    const res = await fetch('/api/user');
    return await res.json();
  } catch (err) { /* ... */ }
}
```

## 5.4 错误处理

- async 函数内的异常（包括 `await` 抛出的）可以被 `try/catch` 捕获，体验与同步代码一致。
- async 函数抛出的错误最终会变成其返回的 Promise 被 **rejected**，所以调用方必须处理，否则会产生 **unhandled rejection**（类似未捕获异常）。
- 顶层调用时用 `.catch()` 兜底：

```js
fetchData().catch(err => console.error('顶层兜底', err));
```

# 第 6 层：实战 —— 陷阱、最佳实践与全景总结

## 6.1 常见陷阱与最佳实践

**1. 忘记 `await`**

```js
async function bad() {
  const data = fetch(...); // 得到的是 Promise，不是数据！
}
```

**2. 在循环中串行 await（性能差）**

```js
// 串行（慢）
for (const url of urls) {
  await fetch(url);
}

// 并行（推荐）
await Promise.all(urls.map(url => fetch(url)));
```

**3. 返回值 vs 抛出错误**

```js
async function f() {
  // return Promise.reject(...) 和 throw 效果类似
  throw new Error('fail'); // 推荐
}
```

**4. 顶层 await**（现代 ES Module 支持）

```js
// 在 ES module 顶层可以直接写
const data = await fetch(...);
```

**5. 错误必须处理**

未捕获的 rejection 会变成 unhandled rejection（类似未捕获异常），顶层用 `.catch()` 或 `try/catch` 兜底，见 5.4。

## 6.2 完整示例（推荐写法）

```js
async function getUserWithPosts(userId) {
  try {
    const [user, posts] = await Promise.all([
      fetch(`/api/users/${userId}`).then(r => r.json()),
      fetch(`/api/users/${userId}/posts`).then(r => r.json())
    ]);
    return { user, posts };
  } catch (err) {
    console.error('获取用户信息失败', err);
    throw err; // 让调用方也能感知
  }
}

// 调用
getUserWithPosts(123)
  .then(result => console.log(result))
  .catch(err => console.error(err));
```

## 6.3 从 Java 视角理解

JavaScript 的异步模型与 Java 的线程 + `Future` / `CompletableFuture` 有本质区别：JS 是**单线程 + 事件循环**，异步主要通过回调、Promise 和 async/await 实现。对照关系如下：

| Java | JavaScript | 说明 |
| --- | --- | --- |
| `CompletableFuture` | `Promise` | 代表未来结果 |
| `future.thenApply / thenCompose` | `.then()` | 链式处理 |
| `future.exceptionally` | `.catch()` | 错误处理 |
| `CompletableFuture.allOf` | `Promise.all` | 全部完成 |
| `CompletableFuture.anyOf` | `Promise.race` / `any` | 竞速 |
| `supplyAsync + thenApply` 链式 | async/await | 语法更清晰 |
| 线程池 + 阻塞 `get()` | 事件循环 + 非阻塞 await | JS 没有真正阻塞线程 |

JS 没有「阻塞当前线程等结果」的概念（除了极少数同步 API），`await` 只是让当前 async 函数暂停，事件循环继续处理其他任务。

## 6.4 全景总结：从下到上串起整条链路

- **单线程** —— JS 只有一个主线程，长同步代码会阻塞页面，所以需要异步。
- **事件循环** —— 耗时操作交给宿主环境（Web APIs / Node 底层）执行，完成后回调进入任务队列，主线程空闲时取出执行；主线程全程没有被阻塞。
- **宏任务与微任务** —— 事件循环的调度规则：每个宏任务结束后**清空所有微任务**再进入下一个宏任务；Promise 回调是微任务，因此比 `setTimeout(..., 0)` 更快，这也是 `await` 能实现「异步代码同步写法」的底层基础。
- **Promise** —— 异步结果的容器 + 状态机 + 链式处理能力，解决了回调地狱。
- **async/await** —— Promise 的语法糖，让异步代码写起来像同步，本质还是 Promise。

**记忆要点：**

- **Promise** = 异步结果的容器 + 状态机 + 链式处理能力。
- **async/await** = 让 Promise 代码写起来像同步，本质还是 Promise。
- 错误处理优先用 `try/catch`（async/await）或 `.catch()`。
- 多个独立异步操作优先用 `Promise.all` 并行。
- 永远不要忘记：`async` 函数返回的是 Promise。

如果你已经熟悉 Java 的 `CompletableFuture`，可以把 Promise 当成更轻量、更语法友好的版本，再配合 async/await 就能写出非常清晰的异步代码。
