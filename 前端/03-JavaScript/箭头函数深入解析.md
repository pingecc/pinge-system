1. 箭头函数**在被创建，外部函数执行时，就已经捕获了外层的函数的this** 
2. 箭头函数在被执行时，**引擎已经知道了这个是箭头函数**，解析this时不会走普通函数那套机制，而是走单独箭头函数的机制，直接拿1）中已经捕获的this 
3. 由于箭头函数在创建之初就绑定了this，所以该箭头函数在任何以地方执行，this永远拿到的是当初创建定义时，指向的那个外部函数的this
# 理解为什么会出现箭头函数

箭头函数（Arrow Function）是在 **ES6（ES2015）** 正式引入的，规范发布于 2015 年。提案由 Brendan Eich 主导，早期讨论大约从 2011–2013 年就开始了（当时还受到 CoffeeScript、C# 等语言的 lambda 语法影响）。浏览器全面支持大致在 2016 年前后。

它主要解决两个问题：

### ⁠0.1 ⁠语法太啰嗦（尤其是回调场景）

以前写匿名函数很冗长，特别是在数组方法、Promise、事件回调里：

```javascript
// ES5
const lengths = materials.map(function(material) {
  return material.length;
});

// ES6 箭头函数
const lengths = materials.map(material => material.length);
```

单表达式时甚至可以省略大括号和 `return`，代码更简洁。

### ⁠0.2 ⁠最核心的痛点：`this` 指向混乱（Lexical this）

普通函数的 `this` 是**动态绑定**的，取决于调用方式：
- 作为对象方法调用 → 指向该对象
- 普通函数调用 / 回调 → 通常指向全局对象（非严格模式）或 `undefined`（严格模式）

这在回调里特别容易出错：

```javascript
const obj = {
  count: 0,
  start() {
    // 普通函数：this 丢失
    setTimeout(function() {
      this.count++;  // 这里 this 不是 obj！
      console.log(this.count);
    }, 1000);
  }
};
```

上面的普通函数传给了setTimeout函数，被它的参数进行接收，在内部会被当作普通函数进行调用，此时它函数体内部的this实际上就是指向的全局对象或者undefined了，无法拿到当初在声明时所在的对象。

以前大家常用两种变通方法：
- `const self = this;`
- `.bind(this)`

```js 
const  obj = {  
    count:0,  
    start() {  
        // 通过变量的存储当前this，然后通过闭包的形式传给内部函数  
        const self = this;  
        setTimeout(function (){  
            console.log('开始执行回调函数')  
            //直接基于闭包的形式来访问  
            console.log('输出 count：' + self.count++)  
        },1000)  
    }  
}  
obj.start()
```

箭头函数没有自己的 `this`，它会**从定义时所在的词法作用域**继承 `this`（Lexical this）：

```javascript
const obj = {
  count: 0,
  start() {
    // 箭头函数：this 就是外层的 obj
    setTimeout(() => {
      this.count++;
      console.log(this.count);  // 正确
    }, 1000);
  }
};
```

这就是它最大的价值——彻底解决了回调中 `this` 丢失的问题。

### ⁠0.3 ⁠需要注意的限制

箭头函数并不是完全替代普通函数，它有意做了这些限制：
- 没有自己的 `this`、`arguments`、`super`
- 不能作为构造函数（不能用 `new`）
- 没有 `prototype`
- 不适合作为对象方法（因为需要动态 `this` 时会失效）

所以实际开发中：
- **回调、函数式风格** → 优先用箭头函数
- **对象方法、构造函数、需要 `this` 动态绑定** → 用普通函数或方法简写

简单总结：**箭头函数是为了让“写短回调 + 正确捕获外层 this”这件事变得自然**，而不是为了取代所有函数。


# 如何理解**从定义时所在的词法作用域**继承 `this`

## ⁠1 ⁠捕获外层this的过程

**过程：**

1. 外层函数开始执行
2. 执行到箭头函数表达式时，**创建**这个箭头函数
3. 创建的瞬间，它把外层当前的 `this` 记下来（闭包）
4. 之后不管这个箭头函数在哪被调用，用的都是创建时捕获的那个 `this`


**代码说明：**
```javascript
const obj = {
  name: "张三",
  start() {
    // 这里 this === obj

    const f = () => {
      // 箭头函数创建时，捕获了上面的 this（也就是 obj）
      console.log(this.name);
    };

    setTimeout(f, 1000);
  }
};

obj.start();   // 1秒后输出：张三
```

如果外层函数被调用时 `this` 不同，箭头函数捕获到的也不同：

```javascript
const f = obj.start;
f();   // 如果严格模式下 this 是 undefined，箭头函数里也会是 undefined
```

## ⁠2 ⁠Lexical如何理解



### ⁠2.1 ⁠1. 函数对象本身就带着“身份”

创建函数时，引擎会在函数对象上打上内部标记（规范里叫 `[[ThisMode]]`）：

| 函数类型       | `[[ThisMode]]` | 有没有自己的 `this` |
|----------------|----------------|---------------------|
| 普通函数       | `"global"` 或 `"strict"` | 有（动态绑定）     |
| **箭头函数**   | `"lexical"`    | **没有**           |

所以箭头函数创建完成后，它自己就声明了：“我不要自己的 `this`，我用外层的。”

### ⁠2.2 ⁠2. 调用时引擎怎么解析 `this`

当执行 `f()` 时，引擎大致做这件事：

```text
调用 f()
  ↓
查看 f 的 [[ThisMode]]
  ↓
如果是 "lexical"（箭头函数）
  → 忽略这次调用方式
  → 直接用创建时捕获的外层 this
  ↓
如果是普通函数
  → 根据调用方式决定 this（obj.f()、f()、f.call() 等）
```

也就是说：**不是调用方“猜”**，而是函数对象自己告诉引擎“我该怎么处理 this”。

### ⁠2.3 ⁠3. “从定义时所在的词法作用域继承 this” 到底是什么意思

更准确的说法是：

> 箭头函数在**被创建的那一刻**，把自己绑定到了当时的**外层词法环境**上（闭包）。  
> 之后每次执行，它都去这个闭包里找 `this`，而不是根据调用方式重新计算。

示例：

```javascript
const obj = {
  name: "张三",
  start() {
    // 此时词法环境里的 this === obj
    const f = () => {
      console.log(this.name);  // 永远指向创建时那个环境的 this
    };
    return f;
  }
};

const callback = obj.start();
callback();          // 直接调用，仍然输出 "张三"
callback.call({});   // 即使用 call 强行改，也无效，还是 "张三"
```

### ⁠2.4 ⁠总结

- 定义/创建时：箭头函数把外层的 `this` 闭包住，并标记自己是 lexical 模式。
- 执行时：引擎一看是箭头函数，就直接用闭包里的那个 `this`，完全不管这次是怎么调用的。
- 所以即使你是普通直接调用 `f()`，引擎也知道它是箭头函数，不会按普通函数的规则去重新绑定 `this`。
